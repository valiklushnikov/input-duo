# Discovery Windows ↔ macOS — двухмашинный E2E runbook

**Дата создания:** 2026-09-26
**Задание:** Task 7 (`.superpowers/sdd/2026-09-26-lan-discovery-hardening/task-7-brief.md`),
план `docs/superpowers/plans/2026-09-26-lan-discovery-hardening.md`.
**Статус:** MANUAL, требует двух реальных машин (Mac + Windows). Матрица ниже
не прогнана — Шаг 4 (сам прогон) выполняет оператор отдельно и дописывает
результаты в этот же файл отдельным коммитом `docs(discovery): E2E results
<дата>`.

**Связанные записи:**
- `docs/superpowers/records/2026-09-26-macos-multicast-discovery-spike.md` —
  подтверждает, что UDP multicast discovery работает между Windows и macOS в
  `.app`, подписанном Personal Team, без `com.apple.developer.networking.multicast`,
  но обнажает главный практический риск: multi-homed Windows (одновременно
  Ethernet и Wi-Fi) может слать multicast только через маршрут по умолчанию,
  и если этот маршрут смотрит не в ту сеть, где находится Mac, доходит **0**
  маячков в обе стороны, хотя рассылка через каждый интерфейс по отдельности
  работает штатно. Это напрямую обосновывает строку **E6** ниже.
- `docs/superpowers/records/validation/fileprovider-e2e-matrix.md` — образец
  оформления MANUAL-матрицы, по которому построен этот файл.

## Предусловия

- На Mac установлен `DuoInput.app`, собранный `packaging/nuitka-build-macos.sh`
  с этой ветки (`feature/lan-discovery-hardening`).
- На Mac разрешён доступ **Local Network** для Duo Input (System Settings →
  Privacy & Security → Local Network), и **после разрешения выполнен
  перезапуск** приложения.
  - Исключение из спайка (`2026-09-26-macos-multicast-discovery-spike.md`,
    S2): на **свежей** установке, пока запрос Local Network ещё висит без
    ответа, первые отправки маячка отклоняются с
    `NetworkError 'Unable to send a message'` — это ожидаемо и не является
    провалом строки; после нажатия **Allow** отправка начинает работать в
    том же процессе, без перезапуска. Перезапуск после Allow всё равно
    рекомендуется как предусловие матрицы, чтобы не путать «уже разрешено
    ранее» с «разрешаю прямо сейчас».
- На Windows — сборка той же ветки, профиль сети **Private** (не Public/Guest
  — иначе Windows Firewall может блокировать входящий UDP независимо от
  правил Duo Input).
- Платы U1/U2 **отключены** на обеих машинах, если конкретная строка матрицы
  не требует иного (см. E8).
- Поле ручного адреса пустое на обеих машинах, если строка не требует иного
  (см. E9).

## Где смотреть

- **Журнал:**
  - Mac: `~/.local/share/DuoInput/logs/`
  - Windows: `%LOCALAPPDATA%\DuoInput\logs\`
  - Ключевые строки, введённые/изменённые этим планом:
    - `discovery_hint address=<адрес>` — coordinator увидел новый адрес пира
      (от платы или от маячка) и решает, можно ли звонить прямо сейчас
      (Task 4).
    - `beacon_send_failed interface=<имя> error=<текст>` — отправка маячка
      через конкретный сетевой интерфейс не удалась (Task 6).
    - `beacon_send_recovered interface=<имя>` — та же отправка снова
      заработала после серии неудач (Task 6).
  - Существующие строки, которые матрица также использует как ориентир:
    - `coordinator_link_attached connection_generation=<N>` — связь реально
      поднята (ровно один раз на поколение).
    - `address_in_use` — TCP-порт слушателя занят (BLOCKED), новый адрес его
      не чинит.
- **Доверие:** `peers.json`
  - Mac: `~/.local/share/DuoInput/peers.json`
  - Windows: `%LOCALAPPDATA%\DuoInput\peers.json`
  - Поле `last_address` обновляется **только** после успешного pinned-TLS
    подключения (`coordinator_link_attached`), а не по факту получения
    маячка или подсказки от платы — маячок сам по себе на диск не пишет.
- **Состояние:** значок в трее и страница «Общий буфер» в настройках Duo
  Input на обеих машинах.
