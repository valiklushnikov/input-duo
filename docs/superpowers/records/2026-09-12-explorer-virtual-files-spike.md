**Машина:** Windows 10 Pro, версия 10.0.19045
**Окружение:** Python 3.12.10; PySide6 6.10.1 (Qt 6.10.1); `.venv`
**Скрипты:** `configurator/tests/transfer/spike_virtual_files.py` (throwaway,

## Что решает этот спайк

Спека `2026-09-12-file-transfer-design.md` выбрала архитектуру C — `IDataObject`
на голом `ctypes` с `FILEDESCRIPTORW`/`FILECONTENTS`/`IStream` — по теории, не
по измерению (§3). Спайк 1 обязан был установить на реальном Проводнике:
принимает ли он такой объект вообще; какой сигнал завершения и отмены
единственно верен (§9, §22 вопрос 1); обязателен ли
`IDataObjectAsyncCapability` (§1, §20, §22 вопрос 3); и что известно про окно
предвыборки (§22 вопрос 2, остаётся открытым до спайка 2 по дизайну).

**Итог: архитектура C работает на реальном Проводнике.** Этот документ
закрывает шлагбаут Task 0.5.

## Поправка к методике брифа

Бриф предполагал две вставки подряд в одном прогоне (одна — до завершения,
другая — до отмены на середине) и полагался на то, что оператор увидит на
экране разделитель «сейчас вставляй». На практике это дало два негодных
прогона, оба задокументированы как повод изменить инструмент, а не методику
руками:

1. **Раунд 4 (`spike-run-a-round4.log`) сам обрубил ещё идущую передачу.**
   Инструмент запускался с фиксированным бюджетом `--seconds 180`, но 4 ГиБ на
   измеренной скорости требуют ~915 с. Лог обрывается на
   `IStream::Read(entry=2, off=810287104, cb=262144) -> 262144` —
   `810549248` из `4294967296` байт, то есть **18.9%** — без какой-либо строки
   `EXIT` или `run ended`, потому что этой строки тогда ещё не существовало.
   Проводник в этот момент ничего не нарушал: копирование оборвал сам
   измерительный скрипт, `OleFlushClipboard`ом отобрав объект у ещё читающего
   потребителя, а на экране это выглядело как ошибка копирования Проводника.
   Это ровно тот дефект, который спайк был обязан не производить, и в первой
   версии произвёл.

2. **Молчание до первой вставки нельзя было отличить от отсутствия вставки
   вообще**, если консоль оператора не видна (свёрнута, вкладка не в фокусе):
   `=== press Ctrl+V in Explorer NOW ===` печатается один раз и без явного
   финального вердикта ничем не отличается от прогона, где `Ctrl+V` вообще не
   нажали, а `GetData` дёргали только фоновые «мониторы буфера обмена»
   (менеджеры истории и т. п.), выдавая Проводник-подобную последовательность
   вызовов без единого реального чтения.

Обе методические проблемы закрыты в инструменте, не в процедуре оператора:

- **Конец прогона по умолчанию — по тишине, а не по бюджету времени.**
  `--idle-seconds` (после первого обращения потребителя) и
  `--paste-window-seconds` (до него), с потолком `--max-seconds`. Фиксированный
  `--seconds N` остаётся доступен, но больше не значение по умолчанию.
- **Каждый прогон обязан закончиться явным вердиктом.** Хвост лога — всегда
  `EXIT 0: no consumer was mid-stream when this run ended` или
  `EXIT 3: ...` с баннером `!!! THIS RUN TRUNCATED A LIVE TRANSFER —
  EXPLORER DID NOT FAIL !!!`, если инструмент оборвал ещё читающего
  потребителя. Прогон больше не может молча закончиться ни в одну сторону.
- **Разделитель фиксируется в логе, а не полагается на то, что оператор его
  увидел.** Строке `=== press Ctrl+V in Explorer NOW - every call below is
  yours ===` предшествует явный расчёт шума фоновых мониторов —
  `clipboard monitors settled after 3.0s; their GetData calls: [...]` — и в
  конце прогона печатается отдельно `GetData calls after the settle marker:
  [...]`. Если этот список пуст — вставки не было вообще, и прогон не
  засчитывается как доказательство; именно так устроен контрольный прогон
  «без вставки» ниже.
- Дополнительно (раунд 3) отменена собственная спасательная логика
  `qapp.exit(1)`, потому что `QCoreApplication.exit()` защёлкивает состояние
  цикла Qt и портит последующие измерения — обнаружено прямым замером
  (`exec()` после `exit(1)` возвращает `-1` за `0.0 ms` вместо реального
  времени), а не предположением.

Ни один из этих трёх прогонов (A, B, C) не был получен старой методикой:
все три прошли через инструмент уже после этой правки.

## Метод

Объект отдаёт три записи одним и тем же `FILEGROUPDESCRIPTORW` (проверено
чтением `spike_virtual_files.py`, `ENTRIES`):

```
("Photos",             is_directory=True,  size=0)
("Photos\\img1.bin",   is_directory=False, size=3*1024*1024)       # 3 МиБ, вложенный файл
("big.bin",            is_directory=False, size=4*1024*1024*1024)  # 4 ГиБ, детерминированный шаблон
```

Содержимое `big.bin` синтетическое и генерируется по чанку за раз
(`synthetic_bytes(entry_index, position, count)` внутри `IStream::Read`, не
хранится и не читается из сети целиком).

`OleSetClipboard` — из выделенного STA-потока. В том же процессе крутится
**видимый** `QProgressBar` с `QTimer` на 16 мс (`Instrument` в
`spike_qt_responsiveness.py`): каждый фактический интервал между тиками
записывается, и это единственный честный измеримый прибор для «UI не
замирает» — картинка на экране, а не наше слово.

Три прогона на реальном Проводнике этой же машины:

- **Run A** — без `IDataObjectAsyncCapability`, доведён до конца
  (`--idle-seconds 45 --max-seconds 3600`).
- **Run B** — `--async-capability`, идентичное действие оператора, доведён до
  конца.
- **Run C** — `--async-capability`, оператор нажал «Отмена» в диалоге
  Проводника на середине потока `big.bin`.

Плюс контрольный прогон без вставки (`--inspect-clipboard`-соседний,
`spike-run-a-round4-no-paste.log`) и сравнение через
`--inspect-clipboard`: наш объект (`ours-reference.log`) и родной ZIP-объект
Проводника (`zip-reference.log`), оба через один и тот же внешний зонд —
`OleGetClipboard` + дамп `IEnumFORMATETC` + серия `QueryGetData`.

```
[  99.774s tid= 19376] QueryGetData(cfFormat=49274, lindex=-1)
   ... (только опрос Preferred DropEffect / Shell IDList Array, 100 c) ...
```

`enum-notimpl`: `IEnumFORMATETC` не реализован → `OleSetClipboard` сам
проваливается с `0x80004001` (`E_NOTIMPL`) — Проводник вообще не получает
объект. `round2`: `OleSetClipboard` уже успешен (`0x00000000`), но за
~100 с ожидания Проводник ни разу не запросил `FileGroupDescriptorW` —
никакого прогресса за пределы фонового опроса `Preferred DropEffect`. Ни
один из этих прогонов не отличался нумерацией `lindex` от финальной версии;
разница — в том, что `IEnumFORMATETC::Next` в финальной версии реально
перечисляет три записи (`Reset() -> S_OK`, три раза `Next(celt=1) -> 1`,
затем `Next(celt=1) -> 0`), как показано в начале Run A/B/C. Именно это, а
не выбор между `lindex=-1` и `lindex=0` в перечислении, — то, что заставило
Проводник впервые запросить дескриптор.

## Разбор результата

**Критерий прохождения выполнен:** `GetData(cfFormat=49278
(FileGroupDescriptorW), ...)` пришёл от настоящего Проводника, после
разделителя `=== press Ctrl+V in Explorer NOW ===`, а парный контрольный
прогон без вставки логирует `GetData calls after the settle marker: []`.
Оба факта процитированы дословно выше.

**Проводник запрашивает `FILECONTENTS` по нуль-базовым `lindex=1` и
`lindex=2`, никогда `lindex=0`** (директория `Photos`) — подтверждено во
всех трёх реальных прогонах (`GetData(cfFormat=49255 (FileContents),
lindex=1, tymed=13)`, затем `lindex=2`). Он делает `Seek(origin=1, offset=0)`
затем `Seek(origin=0, offset=0)` на каждый поток и **ни разу не вызывает
`Stat`** (`Stat calls: []` во всех трёх прогонах) — размеры он берёт из
дескриптора.

**Чтения строго последовательны, по 262144 байт, монотонный offset, без
предвыборки** — ни в одном из трёх прогонов не встречается второй `Read` до
ответа на первый (лог однопоточный по построению и по `tid`), и оба потока
дошли до чистого EOF ровно на границе объявленного размера: `entry=1` на
`3145728` (= 3 МиБ), `entry=2` на `4294967296` (= 4 ГиБ) — деление 64-битного
размера в дескрипторе корректно.

**Жизненный цикл, Run B и C:** `GetAsyncMode -> TRUE`, затем `StartOperation`
на следующей же миллисекунде, **оба до** запроса дескриптора; затем на
завершении — `EndOperation(hResult=0x00000000, effects=1)` (Run B), на
отмене — `EndOperation(hResult=0x800704C7, effects=1)` (Run C). `SetAsyncMode`
и `InOperation` **ни разу не вызваны** ни в одном из двух прогонов.

**Run A, без интерфейса:** завершение объявляется косвенно —
`GetData(ZoneIdentifier)` → `SetData` ×3 → `GetData(Performed DropEffect)` →
`GetData(Logical Performed DropEffect)`, и `Lifecycle calls: []`. Более
ранняя ручная отмена без интерфейса не оставила в логе вообще никакого
отличимого следа (это наблюдение из практики предыдущих ручных прогонов, не
переснято в чистом инструментированном виде — см. «Что не установлено»).

**Отзывчивость Qt:** Run A — `ticks 19689, median 58.6 ms, p99 109.3 ms, max
178.3 ms`; Run B — `ticks 19300, median 57.1 ms, p99 111.5 ms, max 170.1 ms`.
Разница на медиане — 1.5 мс, в пределах шума. Контрольный прогон без вставки
— `median 16.0 ms, p99 16.8 ms, max 17.8 ms`. Каждый вызов во всех трёх
прогонах приходит с одним и тем же `tid` — маршалинг на единственный
STA-поток подтверждён (единственный `tid` на файл: `15240` / `16516` /
`16492`).

**Собственный ZIP-объект Проводника идентичен нашему на каждой
проверенной оси**: анонсирует `FileContents` при `lindex=-1, tymed=4`
(`TYMED_ISTREAM`) и отвечает на индексированный `QueryGetData`
`DV_E_FORMATETC` (`0x80040064`). Отличается только объявлением
`IDataObjectAsyncCapability: True`.

## Что НЕ установлено

Ниже — то, что брифу и спеке нужно было закрыть, но чем эта пара логов не
может честно распорядиться:

- **`InOperation` и `SetAsyncMode` ни разу не были вызваны** ни в Run B, ни в
  Run C. Про их поведение ничего не известно; полагаться на них нельзя.
- **Отмена по синхронному пути (без `IDataObjectAsyncCapability`) наблюдалась
  один раз как полная тишина**, но не в чистом инструментированном прогоне
  этой пары (Run A завершился естественно, а не отменой) — только по памяти о
  более ранних ручных экспериментах. Это не пересмотрено заново с текущим
  инструментом и записано как открытое, а не как измеренный факт.
- **Окно предвыборки (§22, вопрос 2) остаётся открытым до спайка 2 по
  дизайну.** Что известно и подтверждено этой парой прогонов: фактический
  `cb` каждого `Read` — ровно `262144` байт постоянно, без исключений, и
  `Seek` действительно вызывается (`Seek(entry, origin=1, offset=0)` затем
  `Seek(entry, origin=0, offset=0)` на каждый поток, всего по три раза на
  запись, `Seek calls: [(1, 1, 0), (1, 0, 0), (1, 0, 0), (2, 1, 0), (2, 0, 0),
  (2, 0, 0)]` идентично в A/B/C). Оба факта — входные данные для решения
  спайка 2, само решение не принимается здесь.
- **Родной диалог прогресса Проводника** (критерий 7) — не наблюдался нашим
  инструментом ни в одном прогоне; см. таблицу выше.
- **Потребление памяти процесса** (критерий 9) — не измерялось ни в одном
  прогоне; см. таблицу выше.

## Решения контроллера, зафиксированные этим спайком

Ниже — вердикты контроллера с основанием, которое установил именно этот
спайк, а не переоткрытие вопроса заново.

1. **`IDataObjectAsyncCapability` переходит из «условно» в «обязателен»
   (§1, §3).** Спека планировала искать разницу в отзывчивости — её не
   нашлось (58.6 против 57.1 мс на медиане, разница в пределах шума). Разница
   нашлась не там, где её ждали: интерфейс — **единственный** источник явного
   сигнала завершения и отмены. Без него отменённая сессия неотличима от
   зависшей (Run A завершается косвенно через `ZoneIdentifier`/`SetData`,
   `Lifecycle calls: []`; более ранняя синхронная отмена не оставила следа
   вообще).
2. **Источник истины завершения в §9 — `EndOperation`, и его `hResult`
   различает завершение и отмену**, это первая ветка §9, а не запасной
   вариант. Таймаут-сторож остаётся обязательным дополнением дизайна именно
   потому, что без интерфейса отмена молчит совсем: таймаут — единственная
   защита от того случая, когда `EndOperation` недоступен или не пришёл.
3. **Интерфейс не облегчает наш UI.** Каждый вызов маршалируется на наш
   единственный STA-поток, и A и B расходятся на 1.5 мс медианы — то есть в
   пределах шума. Реальное облегчение для продакшн Qt-приложения обязано
   прийти из обслуживания `IStream::Read` без блокировки Qt-потока (§7), а не
   из самого факта объявления интерфейса. Низкая медиана Run C (16.0 мс) —
   артефакт 90-секундного прогона, из которых лишь ~39 с были заняты
   передачей: её нельзя читать как «отмена улучшает отзывчивость».
4. **Ответ `GetAsyncMode` постоянным `TRUE` остаётся как есть**, задним
   числом подтверждено: `SetAsyncMode` Проводник не вызвал ни разу ни в одном
   прогоне, то есть согласовывать в отношении него попросту нечего.
5. **Перечисляемый `lindex` до потребителя не доходит никогда** — OLE
   переписывает его на `-1` в любом случае, что доказывает и сам ZIP-эталон
   (`[2] cfFormat=49255 (FileContents) ... lindex=-1 tymed=4`, при этом
   `GetData` реального Проводника обращается по нуль-базовому `lindex=1/2`
   напрямую, минуя объявленное значение). Два раунда правок, потраченные на
   нейтральную-против-нулевой нумерацию (`enum-notimpl.log`,
   `spike-run-a-round2.log`), были не при чём: до них `OleSetClipboard`
   проваливался целиком (`0x80004001`, `IEnumFORMATETC` не реализован) либо
   успевал, но Проводник ни разу не запрашивал дескриптор за ~100 с ожидания.
   То, что реально заставило Проводник включиться, — рабочая реализация
   `IEnumFORMATETC::Next` (`Reset() -> S_OK`, три `Next(celt=1) -> 1`, затем
   `-> 0`), а не выбор конкретного числа `lindex`.

## Вердикт спайка

Архитектура C — `IDataObject` + `IEnumFORMATETC` + `IStream` на голом
`ctypes` — принята Проводником на реальном рабочем столе, доводит 4 ГиБ до
чистого EOF на границе объявленного размера, корректно обслуживает отмену
через `IDataObjectAsyncCapability`, и не замораживает Qt-интерфейс процесса.
Семь из девяти критериев §20 установлены измерением; два (родной диалог
прогресса, потребление памяти) остаются неизмеренными и не блокируют переход
— оба закрываются добавлением инструментария в последующих фазах, а не
пересмотром архитектуры. **Решение по шлагбауту: Фаза 1 открыта.**
