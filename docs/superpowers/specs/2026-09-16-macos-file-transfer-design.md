# Передача файлов Windows ↔ macOS — дизайн

**Дата:** 2026-09-16
**Статус:** дизайн утверждён по секциям, ожидает плана реализации
**Объём:** `configurator/` целиком; прошивка, протокол устройства и двоичный
формат конфигурации не меняются.
**Предшественник:** `2026-09-12-file-transfer-design.md` (milestone 1, Windows ↔
Windows). Его §18 назвал macOS отдельным milestone и честно оговорил, что
`NSFilePromiseProvider` документирован для drag-and-drop, а поддержка `⌘V` —
неизвестна. Настоящий документ закрывает эту неизвестность спайком и проектирует
обе кросс-платформенные комбинации.
**Спайк-шлагбаум:** `records/2026-09-16-macos-file-promise-spike.md`.

## Цель

Milestone 1 дал `Ctrl+C` в Explorer PC1 → `Ctrl+V` в Explorer PC2 (Windows ↔
Windows). Этот этап добавляет обе комбинации с macOS:

```
Windows → Windows   (готово, milestone 1)
Mac     → Windows    (этот этап; Mac отдаёт, Windows принимает)
Windows → Mac        (этот этап; Windows отдаёт, Mac принимает)
Mac     → Mac         (следствие обоих; не является отдельной работой)
```

Сетевой протокол, валидация путей, модель манифеста, `pipe`, `scanner`, снимки
отправителя и capability `files/2` **не меняются**. Платформенной границей
служит `transfer/platform_files.py`, ровно как `clipboard/platform_backend.py`
для буфера.

## Результат спайка (шлагбаум)

Спайк на macOS 15.1.1 (pyobjc 12.2.2, `.venv-mac`) установил два факта
(`records/2026-09-16-macos-file-promise-spike.md`):

1. **`NSFilePromiseProvider` не материализуется на `⌘V`.** Промис объявлен
   корректно (`writeObjects ok=True`, типы `com.apple.pasteboard.promised-file-*`
   на буфере), но Finder на вставку **не вызывает делегат** ни разу за всё
   наблюдение — файл не появляется. Ленивый промис-путь (аналог Windows
   `IDataObject`+`IStream`, где Проводник тянет байты на вставку) для `⌘V`
   недоступен.
2. **Настоящий `file://` URL на буфере — Finder вставляет копию.** Eager-данные
   на pasteboard переживают выход процесса-владельца; `⌘V` создаёт копию файла в
   целевой папке.

**Прямое следствие.** Приёмник Windows→Mac обязан **материализовать настоящие
файлы на диск (staging)** и класть на буфер их `file://` URL. Инвариант «не
пишем на диск» на приёмнике Mac физически недостижим — это плата, назначенная
спайком, а не выбор дизайна. Второй инвариант — «скопированное и не вставленное
не покидает машину-источник» — сохраняется не нативным ленивым чтением Finder
(его нет), а **явным согласием пользователя перед физической передачей** (§3).

## 1. Объём

### Входит

- **Mac как отправитель (Mac→Windows):** чтение файлового буфера Finder через Qt
  `urls()` тем же каналом `local_file_paths()`, что уже существует; всё
  остальное на отправной стороне переиспользуется без изменений.
- **Mac как приёмник (Windows→Mac):** согласие пользователя, самоуправляемый
  цикл скачивания в staging, вооружение `NSPasteboard` `file://` URL, жизненный
  цикл staging с GC.
- **Настройка** «Incoming files from paired computers»: `Ask before downloading`
  (default) / `Download automatically` (opt-in).
- **Прогресс и отмена** приёма в UI Duo Input на Mac.
- Распространение boundary-тестов на новые `transfer/macos_*` модули.

### Отложено явно, с причиной

| Отложено | Причина |
|---|---|
| **Ленивый staging по чтению `file://` (вариант C)** | Rejected сейчас, см. §6. Нельзя обеспечить приемлемый Finder UX для больших файлов с прогрессом/отменой: Finder морозится на время синхронного скачивания. Возврат — только если будущий research по macOS API найдёт нормальное асинхронное нативное поведение |
| macOS packaging (`.app`/подпись/нотаризация/`.dmg`) | как в clipboard-parity: разработка и приёмка из `.venv-mac`. Apple Developer Program не является prerequisite |
| изменение сетевого протокола | `wire` остаётся; шесть `FILE_*` и `files/2` покрывают обе стороны |
| remote Move, resume, несколько одновременных передач, compression, history | те же причины, что в milestone 1 (§1 предшественника); модель их не запрещает |
| владелец/ACL/права при кросс-платформенном копировании | Windows-строгий `paths.py` — надмножество; метаданные прав не переносятся |

## 2. Mac как отправитель (Mac→Windows)

Отправная сторона в milestone 1 сделана платформо-нейтральной, и это
установлено чтением кода, а не предположено:

- `clipboard/formats.py` уже содержит `local_file_paths(mime_data)` — читает
  локальные `file://` пути отдельным каналом от синхронизируемых форматов,
  нормализует разделитель через `str(Path(...))`.
- `clipboard/windows_backend.py:69` строит снимок как
  `ClipboardSnapshot(collect_payloads(mime_data), local_file_paths(mime_data))`.
- `app.py` соединяет `snapshot_taken → _offer_files_from → offer_local_files`, а
  дальше `transfer/service.py` делает `scan()` и `SnapshotRegistry.publish()`.
  Отдача чанков (`FILE_READ → FILE_CHUNK`) в `source.py`/`service.py`
  платформо-нейтральна.

**Единственный дефект симметрии.** `clipboard/macos_backend.py:57` строит снимок
как `ClipboardSnapshot(collect_payloads(mime_data))` — **без** второго
аргумента, то есть с пустыми `file_paths`. Правка: передать
`local_file_paths(mime_data)` вторым аргументом, симметрично Windows-бэкенду.
После этого весь путь Mac→Windows работает существующим кодом.

**Микро-проверка при реализации** (не блокер дизайна): Finder Cmd+C по файлам
кладёт `file://` URL, которые Qt отдаёт через `mime_data.urls()`. Спайк
подтвердил обратное направление (`file://` на буфере читаем и вставляем); чтение
Finder-копии проверяется двухмашинной приёмкой и unit-тестом на фейковом
`QMimeData` с `file://` URL.

**Приёмная Windows-сторона не меняется** — она уже принимает `FILE_OFFER` от
любого пира с `files/2` и предъявляет виртуальные файлы Explorer.

## 3. Mac как приёмник (Windows→Mac): offer → Accept → staging → ⌘V

Продуктовая модель, а не обход ограничения: **копирование создаёт offer; Accept
авторизует физическую передачу; `⌘V` работает с локально подготовленным
объектом.**

### Поток

```
PC1 (Windows) Ctrl+C в Explorer
  │ FILE_OFFER{transfer_id, entries[], total_bytes, skipped[]}  ← только описание
  ▼
Mac: манифест целиком проходит sanitize_manifest (reuse paths.py)
  │
  ├─ настройка = Ask  → нативный промпт «PC1 хочет передать N файлов (X МБ)»
  │                      Принять / Отклонить
  └─ настройка = Auto → staging стартует сразу
  │
  ▼ проверка free_space >= total_bytes + reserve
STAGING <transfer_id>/ создаётся; для каждой записи самоуправляемый цикл:
     FILE_READ → FILE_CHUNK → запись в staging-файл → следующий
     (один запрос в полёте → потолок памяти = один чанк; наш прогресс и Отмена)
  │
  ▼ по завершении — host-only вооружение NSPasteboard:
     file:// URL корневых элементов staging-дерева
  │
Mac: ⌘V в любой папке Finder → Finder копирует из staging в цель (мгновенно)
```

### Почему приёмник Mac проще Windows-приёмника

На Windows приёмник **пассивен**: Explorer тянет байты через синхронный
`IStream::Read` на COM-потоке, и `windows_com.py` (858 строк vtables), выделенный
STA-поток, мост `IStream→PeerLink` и `ChunkPipe` существуют **только** чтобы
обслужить этот pull, не блокируя Qt. На Mac Finder не тянет — **тянем мы**.
Поэтому COM, STA-поток, мост и `ChunkPipe` на приёмнике Mac **не нужны вовсе**.
Цикл скачивания — прямой конечный автомат в Qt-потоке: один `FILE_READ` в полёте,
на `FILE_CHUNK` пишем в файл и шлём следующий. Это самый большой источник
переиспользования протокола при наименьшей платформенной поверхности.

### Согласие и настройка

Настройка `incoming_files ∈ {ask, auto}`, default `ask`, хранится тем же
механизмом, что остальные настройки приложения. В режиме `ask` — модальный/
нативный промпт с числом файлов и суммарным размером из манифеста. В режиме
`auto` — staging без промпта (сознательный opt-in для доверенных paired machines).

**Терминология авторизации.** Без предварительной авторизации пользователя
данные не передаются: авторизацией является **Accept для конкретного offer** либо
**ранее включённый пользователем режим Auto**. Auto — это не «согласие на данный
transfer», а заранее данное постоянное разрешение; поэтому «явным согласием на
конкретный offer» его называть нельзя, а «предварительной авторизацией» — можно.
Пока авторизации нет (в режиме `ask` до Accept), ни один `FILE_READ` не уходит.

### Потолок памяти

Один запрос в полёте → в процессе никогда не живёт больше одного чанка, как на
Windows (milestone 1 §8 подтвердил измерением `pipe high_water = 1`). Здесь это
ещё проще: нет `ChunkPipe`, есть последовательный цикл, и глубина буфера
структурно равна одному чанку.

### Жизненный цикл staging

Факт вставки в Finder **недетектируем** (paste-хука нет), поэтому «после вставки
удалить» невозможно, а «новый offer → удалить предыдущий staging» **запрещено**:
это инвалидировало бы ещё живой `file://` в `NSPasteboard`, на который Finder
может сослаться при отложенном `⌘V`.

```
DOWNLOADING ──завершено──▶ READY ──TTL / disk-budget──▶ EXPIRED / EVICTED
     │
     └─ cancel / error / обнаружение при startup ──▶ немедленное удаление
```

- Каждый transfer получает **отдельный** каталог `<transfer_id>` под
  `~/Library/Caches/duo-input/incoming/`.
- **Незавершённый (DOWNLOADING)** удаляется при cancel/error и при startup
  recovery (обнаружен незакрытый каталог после падения/перезапуска).
- **READY сохраняется** независимо от нового offer и от нормального выхода
  приложения — потому что `NSPasteboard`/Finder может продолжать ссылаться на его
  `file://`.
- **Garbage collection** при startup и периодически, best-effort (ошибка
  удаления не ломает приложение):
  1. удалить READY старше TTL (default 24 ч);
  2. если превышен disk budget — вытеснить самые старые READY по LRU/age;
  3. текущий clipboard-backed transfer в рамках текущего процесса по возможности
     не вытеснять.
- **Перед Accept/Auto** — проверка `free_space >= total_bytes + reserve`; при
  нехватке места offer отклоняется с внятной причиной, staging не создаётся.

### Ранний implementation-checkpoint: host-only + несколько `file://` URL

Спайк подтвердил, что Finder вставляет **один** `file://` URL. Но приёмник
объявляет `file://` URL **корневых элементов дерева** — а их может быть
несколько (несколько файлов/папок в одном `Ctrl+C`), и они должны быть
опубликованы **host-only** (`NSPasteboardContentsCurrentHostOnly`), как ленивые
форматы буфера. Это **последняя OS-specific предпосылка** цепочки staging →
Finder, и её нельзя оставлять на конец.

Поэтому она — не «микро-проверка при реализации», а **первая задача плана после
согласования**, до написания всего Mac-приёмника: короткий подтверждающий спайк,
который кладёт host-only несколько заранее существующих `file://` URL на
`NSPasteboard` и проверяет, что `⌘V` в Finder создаёт **все** соответствующие
копии, а содержимое не всплывает на устройствах Handoff. Если поведение
отличается от ожидаемого (например, host-only ломает файловые URL или Finder
берёт только первый) — это меняет форму вооружения буфера, и узнать это нужно
**до** цикла скачивания, а не после. Результат записывается в тот же record
спайка либо в отдельный.

## 4. Компоненты

```
transfer/macos_files.py       приёмный backend Mac: конечный автомат скачивания,
                              staging, прогресс/отмена, жизненный цикл каталогов
                              — Qt + чистый Python, БЕЗ pyobjc
transfer/macos_pasteboard.py  единственный pyobjc-модуль подсистемы: host-only
                              вооружение NSPasteboard списком file:// URL.
                              Зеркало clipboard/macos_pasteboard.py — узкий,
                              наружу минимум функций
transfer/platform_files.py    +darwin ветка в create_file_backend (ленивый импорт)
```

Цикл скачивания и жизненный цикл staging — **ядро/Qt без pyobjc**, чтобы
тестировать на поддельной связи и `tmp_path` без AppKit. AppKit трогает только
`macos_pasteboard.py`. Это тот же приём изоляции, что уже принят для буфера
(`clipboard/macos_pasteboard.py` — единственный, кто импортирует pyobjc).

**Ленивые импорты фабрики** (как `platform_files.py` сегодня): сборка под Windows
не тянет `macos_*`, сборка под macOS не тянет `windows_files`/`windows_com`/
ctypes-COM. Обе половины изолированы в runtime-графе.

По образцу существующего `test_only_macos_pasteboard_touches_pyobjc`:

1. `transfer/macos_files.py` не импортирует AppKit/Foundation/objc и не
   импортирует `PySide6.QtWidgets`;
2. **только** `transfer/macos_pasteboard.py` может импортировать pyobjc;
3. `transfer/macos_pasteboard.py` не импортирует `PySide6` вовсе (тот же приём,
   что для `windows_com.py` — не дать дёрнуть Qt из чужого контекста);
4. `macos_files.py` не импортирует `transfer.windows_*`.

## 6. Вариант C — rejected сейчас (зафиксировано)

**Ленивый `file-url` провайдер** (`NSPasteboardItem.setDataProvider_forTypes_`
для `public.file-url`, staging на чтение = на вставке) отклонён как основной и
запасной путь этого этапа. Причина не в сложности реализации, а в UX:
провайдер обязан вернуть URL синхронно, значит скачивание идёт **внутри**
callback'а на вставку — Finder заморожен на всё время передачи, без нативного
прогресса и без отмены. Для «20 ГБ» это неприемлемо ровно так же, как вариант B
(lazy staging) был неприемлем для Windows-приёмника milestone 1.

Возврат к C возможен **только** если последующий research по macOS API найдёт
способ получить нормальное асинхронное нативное file-promise поведение на `⌘V`
(с прогрессом и отменой). До тех пор C не реализуется, и это решение, а не
пробел. Спайк на саму осуществимость ленивого `file-url` (читает ли Finder
lazily предоставленный `public.file-url`) в этом этапе не проводится — он не
нужен, пока C отклонён по UX, а не по осуществимости.

## 7. Протокол и совместимость

Протокол milestone 1 покрывает обе стороны без изменений: шесть `FILE_*`
(`FILE_OFFER`, `TRANSFER_BEGIN`, `FILE_READ`, `FILE_CHUNK`, `FILE_ERROR`,
`TRANSFER_END`) симметричны по ролям. Mac-приёмник — тот, кто шлёт `FILE_READ` и
принимает `FILE_CHUNK`; Windows-отправитель уже эту роль обслуживает.
Mac-отправитель — тот, кто отдаёт `FILE_CHUNK` по `FILE_READ`; Windows-приёмник
уже эту роль обслуживает. Capability `files/2` объявляется обеими платформами;
без неё `FILE_*` не отправляется и не принимается (защита старого пира —
milestone 1 §2, факт 4). `PROTOCOL_MAJOR` не поднимается.

`paths.py` остаётся Windows-строгим и на macOS: запреты Windows — надмножество, и
ослаблять их под другую платформу незачем (milestone 1 §18). Манифест,
пришедший на Mac, проходит тот же `sanitize_manifest`, что и на Windows.

## 8. Тестирование

Стратегия как в проекте: offscreen Qt + фейки; настоящий AppKit/сеть в
unit-тестах не участвуют.

### Модульные, без Qt/pyobjc/сети

- **Mac-отправитель:** `snapshot_from` на фейковом `QMimeData` с `file://` URL →
  снимок несёт `file_paths`; parity-тест «один абстрактный `QMimeData` даёт
  одинаковый файловый канал на Windows и на Mac».
- **Цикл скачивания** (`macos_files.py` без pyobjc): на поддельной связи по
  образцу `device/emulator.py` — `FILE_READ`/`FILE_CHUNK` round-trip в staging;
  все переходы `DOWNLOADING → READY`, cancel, error, усечённый `FILE_CHUNK`
  (`truncated`), разрыв связи, повторный `transfer_id`.
- **Жизненный цикл staging** на `tmp_path`: DOWNLOADING удаляется на cancel/error
  и на startup recovery; READY переживает «новый offer» и «нормальный выход»; GC
  по TTL; disk-budget/LRU-вытеснение; best-effort (смоделированная ошибка
  удаления не роняет процесс); текущий clipboard-backed transfer не вытесняется.
- **Проверка места:** `free_space < total_bytes + reserve` → offer отклонён,
  staging не создан.

### Интеграционные, на временных каталогах и настоящем TLS на loopback

`sender/` и `receiver/` во `tmp_path`, данные детерминированы. Размеры: 0 Б, 1 Б,
1 КиБ, 1 МиБ, 100+ МиБ. Случаи: один файл; несколько; вложенные каталоги; имя в
Unicode; нулевой файл; разрыв посередине; отмена посередине; усечённый кадр;
повторный `transfer_id`.

### Тест памяти

Синтетический файл на несколько ГиБ (генерируется, на диске не хранится).
Утверждение: рост памяти процесса-приёмника ограничен и не масштабируется с
объёмом (глубина = один чанк). `tracemalloc` + грубая проверка RSS. Медленный
маркер.

### Граничные тесты

Четыре правила §5. Плюс существующий приём «список модулей не пуст»
(`_package_modules` отказывается зеленеть на нулевом обходе).

### Production call path

- при включённом переключателе Mac-приёмник действительно создаётся в
  `app.configure_runtime`, а не только существует как модуль;
- переключатель «Передача файлов» в трее поднимает и останавливает подсистему на
  Mac;
- настройка Ask/Auto действительно влияет на наличие промпта.

### Ручные проверки на двух машинах (record)

- Mac→Windows: `⌘C` в Finder → `Ctrl+V` в Explorer; один файл, дерево папок,
  Unicode-имя, крупный файл; прогресс и отмена на Windows-приёмнике.
- Windows→Mac: `Ctrl+C` в Explorer → промпт Accept на Mac → прогресс/отмена →
  `⌘V` в Finder; повторный `⌘V` в другую папку из того же READY staging;
  проверка, что READY переживает следующий offer.
- Режим Auto: `Ctrl+C` на Windows материализует staging без промпта.
- host-only: содержимое не всплывает на других устройствах Handoff.

## Сводка инвариантов

1. Сетевой протокол, `paths.py`, `model.py`, `pipe.py`, `scanner.py`,
   `source.py`, `wire.py` не меняются; `PROTOCOL_MAJOR` не поднимается.
2. Только `transfer/macos_pasteboard.py` импортирует pyobjc; `macos_files.py`
   свободен от AppKit и `QtWidgets`; фабрика с ленивыми импортами изолирует
   Windows- и macOS-графы.
3. На приёмнике Mac без предварительной авторизации пользователя данные не
   передаются: авторизация — Accept для конкретного offer либо ранее включённый
   режим Auto (не «согласие на данный transfer», а заранее данное разрешение).
4. Потолок памяти приёмника = один чанк (один запрос в полёте, без `ChunkPipe`).
5. READY staging сохраняется независимо от нового offer и нормального выхода;
   «новый offer → удалить предыдущий staging» запрещено; incomplete удаляется на
   cancel/error и startup recovery.
6. GC best-effort по TTL (24 ч) + disk-budget/LRU; перед transfer — проверка
   свободного места.
7. host-only при вооружении буфера на macOS.
8. Вариант C (ленивый file-url провайдер) не реализуется в этом этапе.

## Проверить при реализации (микро-проверки, не блокеры дизайна)

- Отдаёт ли Qt `file://` URL из Finder Cmd+C через `mime_data.urls()` (ожидается
  да; обратное направление спайк подтвердил).
- Значения TTL, disk budget и reserve — стартовые константы, уточняются при
  реализации без изменения модели.

> Host-only вооружение `NSPasteboard` несколькими `file://` URL — **не** здесь:
> это ранний implementation-checkpoint (§3, первая задача плана), а не микро-
> проверка, потому что это последняя OS-specific предпосылка цепочки.
