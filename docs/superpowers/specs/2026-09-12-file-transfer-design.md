# Передача файлов между компьютерами — дизайн

**Дата:** 2026-09-12
**Статус:** утверждён для планирования
**Объём:** `configurator/` целиком; прошивка, протокол устройства и двоичный
формат конфигурации не меняются.
**Платформа M1:** Windows ↔ Windows. macOS — граница абстракции, не реализация.
**Предшественник:** `2026-09-03-shared-clipboard-design.md` — его §14 назвал
файлы milestone 2 и предпочёл WebDAV. Настоящий документ это предпочтение
отменяет; основание — §2, факт 6.

## Зачем

Два ноутбука делят мышь и клавиатуру через Duo Input и делят буфер обмена, но
не делят файлы. Задача: `Ctrl+C` на файле в Проводнике PC1, переключение,
`Ctrl+V` в любой папке на PC2 — и файл там. Это должно ощущаться как обычное
системное копирование, а не как отдельное окно «отправить файл».

Три свойства нельзя потерять по дороге, потому что на них держится подсистема
буфера обмена: содержимое не пишется на диск; скопированное и не вставленное
не покидает машину; данные уходят только в установленное соединение с явно
спаренным пиром.

И одно новое свойство обязано появиться: **потребление памяти не зависит от
размера файла**. Файл на 20 ГБ не имеет права превратиться в 20 ГБ в RAM.

## 1. Объём

### Входит в M1

- чтение `CF_HDROP` источника через Qt `urls()`; обход дерева; манифест
- `sanitize_relative_path()` со всеми запретами (§11) — целиком наша ответственность
- reparse points (junction, symlink) на источнике **не раскрываются**: запись
  пропускается и попадает в `skipped[]`; PC2 сообщает, сколько ссылок пропущено
- `IDataObject` + `IEnumFORMATETC` + `IStream` на голом `ctypes`
- `IDataObjectAsyncCapability` — **условно**: заложен в дизайн, обязателен в
  production только если спайк 1 покажет наблюдаемую разницу (§3, §20, §22
  вопрос 3). Если разницы нет — выбрасывается, а не остаётся на всякий случай
- `FILEGROUPDESCRIPTORW` с вложенной структурой папок
- `CFSTR_PREFERREDDROPEFFECT = DROPEFFECT_COPY` **всегда**, даже если источник
  был `Ctrl+X`
- выделенный STA-поток; `ChunkPipe`; offset-based pull; ограниченная память
- шесть типов сообщений; capability negotiation; `setReadBufferSize` и
  водораздел записи в `PeerLink`
- один активный transfer на пира; внутри — записи в том порядке, в котором их
  просит Проводник
- отмена, разрыв связи, исчезнувший и изменившийся источник
- сигналы `transfer_started`, `transfer_progress`, `transfer_completed`,
  `transfer_failed`, `transfer_cancelled`; строка прогресса и «Отмена» на
  странице; живой переключатель «Передача файлов» в трее — сегодня
  `ui/tray.py:63` это `setEnabled(False)`, то есть заглушка
- диагностика: `bytes_sent`, `bytes_received`, `current_rate`, `elapsed`,
  `chunk_count`, `pipe_high_water`

### Отложено явно, с причиной

| Отложено | Причина |
|---|---|
| **remote Move (`Ctrl+X`)** | нужен подтверждённый протокол завершения всей операции и безопасная политика удаления. Удаление файлов на другой машине по сети необратимо; цена ошибки несопоставима с удобством |
| resume | Проводник сам решает судьбу обрыва; запросить возобновление некому. Протокол уже offset-based, поэтому цена добавления позже низкая |
| несколько одновременных передач | один активный transfer существенно упрощает автомат; модель расширение не запрещает |
| compression | LAN не узкое место; CPU дороже |
| transfer history | та же причина, что у истории буфера в M1: не входит в задачу и умножает риск |
| cloud relay, дедупликация, delta sync | вне задачи |
| macOS `NSFilePromiseProvider` | отдельный milestone; см. §18 и честную оговорку там |
| вставка не в Проводник (Word, почта) | `FILECONTENTS` понимают многие приложения, но не все. В M1 один механизм и документированное ограничение, а не подстраховка вторым путём |
| владелец, ACL, права доступа | Windows ↔ Windows не требует. Кросс-платформенно — отдельное решение |
| более одного пира | как в M1 буфера обмена |
| перенос `clipboard/wire.py` → `link/wire.py` | unrelated refactoring для M1. Условие переезда названо в §5 |

## 2. Что установлено исследованием, до всякого дизайна

Восемь фактов ограничивают решение сильнее любых предпочтений. Факты 1–5 и 8 —
из чтения репозитория; факты 6 и 7 измерены на целевой машине, и их вывод
приведён дословно.

**1. `RemoteMimeData` (`clipboard/backend.py:57`) для файлов непригодна.** Она
отдаёт `QByteArray` целиком из памяти. Файлам нужен не байтовый payload, а
поток. Это не расширение класса, а второй, отдельный механизм.

**2. Шов для файлов уже прорезан в нужном месте.** `clipboard/formats.py:35`
(`_WEB_SCHEMES`) осознанно вырезает `file://` из `text/uri-list` с
комментарием «файлы — отдельный milestone». Значит `CF_HDROP` источника
читается через Qt без единой строки нативного кода: `mimeData.urls()` даёт
абсолютные локальные пути.

**3. В транспорте нет никакого backpressure.** `PeerLink.send()`
(`clipboard/peer.py:98`) — безусловный `socket.write()`; `QSslSocket`
буферизует в память без границы. `_on_ready_read()` (`peer.py:147`) делает
`readAll()` в `FrameAssembler`, который тоже растёт без границы. Плюс
`MAX_FRAME_BYTES = 32 MiB + 64 KiB` (`wire.py:23`) — жёсткий потолок кадра.
Поток файлов обязан добавить окно и ограничить буферы; это отдельная работа, а
не мелочь.

**4. Неизвестный тип сообщения рвёт соединение целиком.** `_decode_payload`
бросает `WireError` → `_on_ready_read` → `_fail()` → `abort()`. Новый клиент,
отправивший `FILE_*` старому, убьёт заодно и буфер обмена.
**Вывод: capability negotiation обязательна, но подъём major не нужен** —
`PROTOCOL_MINOR` сегодня ни на что не влияет (`coordinator.py:535` сверяет
только major).

**5. `ClipboardService._fetch` крутит вложенный `QEventLoop` в GUI-потоке.**
Кадры, пришедшие внутрь этого цикла, обрабатываются реентрантно. Файловый
конечный автомат внутри этого цикла был бы источником дефектов, которые
невозможно воспроизвести. Отсюда: `ClipboardService` не расширяется.

**6. WebDAV — путь, предпочтённый предыдущей спекой, — выбывает. Измерено:**

```
WebClient service:     Stopped / Manual
HKLM\SYSTEM\CurrentControlSet\Services\WebClient\Parameters
  FileSizeLimitInBytes:     50000000      ← 50 МБ, дефолт Windows
  SendReceiveTimeoutInSec:  60
```

Потолок поднимается только правкой `HKLM`, то есть правами администратора,
которых у приложения по политике нет (`PrivilegesRequired=lowest` в
`packaging/duo-input.iss`). Для требования «20 ГБ» этот путь мёртв. Записано
здесь, чтобы решение не пересматривали заново.

**7. Семантика разделения доступа `open()` на Windows. Измерено** (probe,
Windows 10 Pro 10.0.19045, CPython 3.12.10):

```
Мы держим open(path, "rb"). Другой процесс тогда может:
  открыть на чтение              ALLOWED
  открыть на запись и записать   ALLOWED   ← байтового снимка НЕТ
  усечь файл до 16 байт          ALLOWED   ← и размер меняется под нами
  удалить файл                   BLOCKED (PermissionError winerror=32)
  переименовать файл             BLOCKED (PermissionError winerror=32)

os.fstat(наш fd) после чужой записи: size 16, mtime_ns обновился
мы продолжаем читать тот же файловый объект: b'BAAAAAAA'
```

То есть `open()` в CPython на Windows берёт
`FILE_SHARE_READ | FILE_SHARE_WRITE`, но **не** `FILE_SHARE_DELETE`. Отсюда два
следствия, оба важные и оба разобранные в §10: удержание дескриптора **не**
даёт неизменяемость байтов, но **даёт** невозможность подмены пути; а
`os.fstat(fd)` — честный детектор изменения, не требующий повторного обращения
к пути.

**8. Ни `pywin32`, ни `comtypes` в проекте нет.** Только `ctypes` (stdlib),
PySide6 и `cryptography`; `pyobjc` — только под darwin
(`requirements-build.txt`). Прецедент голого Win32 через `ctypes` в
репозитории уже есть: `tests/clipboard/spike_read_clipboard.py`.

## 3. Три архитектуры и выбор

### A. Eager staging — качаем при получении объявления

PC2, получив объявление, сразу тянет всё в staging-каталог и кладёт настоящий
`CF_HDROP` на локальные пути. Проще всего, COM не нужен, вставка нативна.

**Отклонено:** убивает свойство «скопированное и не вставленное не покидает
машину», которое подсистема буфера защищает тремя поясами. 20 ГБ уезжали бы на
каждый `Ctrl+C`, даже если вставки не будет никогда.

### B. Lazy staging — отложенно отрисовываемый `CF_HDROP`

`CF_HDROP` объявляется как delay-rendered формат; `WM_RENDERFORMAT` на
`Ctrl+V` запускает скачивание в staging, потом возвращает пути. Ленивость есть,
COM-объект не нужен.

**Отклонено как основной путь:** Проводник на всё время скачивания заморожен —
он ждёт `GetData`, у него нет ни прогресса, ни отмены. Спайк 2026-09-03
(`records/2026-09-03-lazy-clipboard-spike.md`) уже измерил этот путь для буфера
на этой же машине: вставляющее приложение ждёт ответа. Для 32 МиБ приемлемо,
для 20 ГБ — нет. Плюс двойная запись на диск.

**B остаётся официальным запасным путём** — но только при доказанном
техническом блокере в C, который нельзя разумно исправить. Не при том, что C
сложнее.

### C. Virtual files — `IDataObject` + `FILEDESCRIPTORW` / `FILECONTENTS` / `IStream`

**Выбрано.**

```
PC1 Ctrl+C в Проводнике
  │ Qt читает CF_HDROP как urls() → обход дерева → TransferManifest
  ▼
FILE_OFFER{transfer_id, entries[]}   ← только описание, ни одного байта
  │
  ▼ PC2: OleSetClipboard(наш IDataObject), объявляющий
       CFSTR_FILEDESCRIPTORW        имена, размеры, атрибуты всего дерева
       CFSTR_FILECONTENTS           TYMED_ISTREAM, lindex = индекс записи
       CFSTR_PREFERREDDROPEFFECT    DROPEFFECT_COPY
       маркер происхождения         (см. §14)

PC2 Ctrl+V в любой папке
  │ Проводник: GetData(FILEDESCRIPTOR) → создаёт дерево, проверяет место
  │ Проводник: GetData(FILECONTENTS, lindex=i, TYMED_ISTREAM) → наш IStream
  │ IStream::Read(cb) ──FILE_READ──▶ PC1 ──FILE_CHUNK──▶ отдаём байты
  ▼ Проводник пишет прямо в целевой файл
```

**Причина выбора — не техническая красота, а объём работы.** C переносит
половину требований на Проводник:

| Требование | Кто это делает в C |
|---|---|
| destination root выбирает получатель | Проводник — папка, где нажали `Ctrl+V` |
| политика перезаписи существующего файла | Проводник, родным диалогом «заменить / пропустить / оба» |
| `.partial` и атомарное переименование | Проводник, своим `.tmp` |
| прогресс и отмена | Проводник |
| создание вложенных папок | Проводник |
| проверка свободного места | Проводник |
| валидация относительных путей | **мы** (§11) — единственное, что остаётся нашим |

То есть самый сложный технически вариант оказывается самым дешёвым по объёму
M1. Это единственное основание его рекомендовать.

Дополнительно C сохраняет свойство «содержимое не пишется на диск»: файлы
читаются из своего исходного места, staging не существует, в нашем процессе
никогда не живёт больше одного чанка.

### Реализация COM: голый `ctypes`, не `comtypes` и не `pywin32`

Причина не эстетическая.

- Нужны только **стандартные** интерфейсы: `IUnknown`, `IDataObject`,
  `IEnumFORMATETC`, `IStream`, `IDataObjectAsyncCapability`. Ни typelib, ни
  кодогенерации, ни записи в реестр. OLE уже содержит готовые proxy/stub для
  `IDataObject` и `IStream` — именно поэтому межпроцессный маршалинг работает
  без нашего участия и этот путь вообще осуществим.
- `comtypes` генерирует код в рантайме в кеш-каталог, что прямо враждебно
  Nuitka standalone. У проекта уже есть открытый риск упаковки нативной части
  (`cryptography`, §18 спеки буфера). Второй такой риск не нужен.
- `ctypes` — stdlib. Ноль новых строк в `requirements-build.txt`.

`comtypes` возвращается в рассмотрение только если спайк 1 покажет, что vtable
на `ctypes` не собирается по причине, которую нельзя обойти.

### `IDataObjectAsyncCapability` — заложен, но не объявлен доказанным

Теория говорит: без него Проводник извлекает файлы на своём UI-потоке, его
диалог прогресса не перерисовывается, и нативный UX получается только на
бумаге. **Эта теория не принимается как факт.** Спайк 1 прогоняет оба режима —
с интерфейсом и без — и записывает наблюдаемую разницу (§20). Если разница
подтверждена, интерфейс становится обязательным в production. Если нет —
выбрасывается.

(`platform/windows/...`) не заводится: в репозитории такого слоя нет, а
`clipboard/platform_backend.py` уже показывает принятый здесь приём —
единственная ветка по `sys.platform` с ленивыми импортами внутри ветвей.

| Файл | Изменение | Почему |

| `clipboard/windows_backend.py` | `is_private()` узнаёт обёрнутое написание маркера | §14 — это готовый дефект |

**Не меняются ни строкой:** `identity.py`, `trust.py`, `pairing.py`,
`discovery.py`, `listener.py`. Личность, доверие, парринг и TLS — общие для
обеих подсистем, и это установлено чтением кода, а не предположено.

**`ClipboardService` не расширяется** — §2, факт 5.

### Четыре новых правила в `test_boundaries.py`

1. `transfer/` никогда не импортирует `PySide6.QtWidgets`;
2. `ctypes` разрешён только в `windows_com.py` и `windows_files.py`;
3. `windows_com.py` не импортирует `PySide6` вовсе;
4. `model.py`, `paths.py`, `pipe.py`, `scanner.py` не импортируют ни `PySide6`,
   ни `transfer.windows_*`.

Правило 3 — не стиль. Это единственный механизм, который через полгода не даст
кому-нибудь дёрнуть `QSslSocket` из COM-потока, потому что «так короче».
Существующий тест уже применяет ровно этот приём к `pyobjc`
(`test_only_macos_pasteboard_touches_pyobjc`), так что приём в репозитории
принят, а не изобретён здесь.

### Одно осознанное неудобство

`transfer/` импортирует `duo_input.clipboard.wire`. Честное имя этого модуля
теперь — `link/wire.py`. Переезд в M1 **не делается**: `MAX_FRAME_BYTES`
считается от `clipboard/offer.py:MAX_CONTENT_BYTES`, поэтому переезд тянет ещё
два модуля и шесть тестов — работа, не относящаяся к задаче. Условие переезда
названо явно: **когда появится третья подсистема поверх `PeerLink` либо когда
эта зависимость начнёт реально мешать.**

## 6. Windows: виртуальные файлы

Объявляемые форматы:

- `CFSTR_FILEDESCRIPTORW` (`FILEGROUPDESCRIPTORW`): счётчик и массив
  `FILEDESCRIPTORW`. `cFileName` несёт **относительный** путь с обратными
  слэшами, поэтому вложенная структура передаётся самим дескриптором, а папки
  помечаются `FILE_ATTRIBUTE_DIRECTORY`. `nFileSizeHigh/Low` из манифеста дают
  Проводнику и полосу прогресса, и проверку свободного места до начала.
  `ftLastWriteTime` — из манифеста.
- `CFSTR_FILECONTENTS` с `TYMED_ISTREAM`; `FORMATETC.lindex` — индекс записи в
  группе.
- `CFSTR_PREFERREDDROPEFFECT` = `DROPEFFECT_COPY`, **всегда**.
- маркер происхождения (§14).

### `Ctrl+X` на источнике

Объявление может запомнить исходный `Preferred DropEffect` в поле
`drop_effect` — **исключительно для диагностики**. PC2 публикует и обрабатывает
это всегда как `DROPEFFECT_COPY`. Файлы на PC1 не удаляются ни при каких
условиях. Remote Move отложен (§1) и требует своего протокола завершения.

### Размер `cFileName`

Поле — `WCHAR[MAX_PATH]`, то есть 259 значимых UTF-16 единиц плюс терминатор.
Это жёсткая граница формата, а не наше решение, и она входит в §11 как одно из
условий отказа.

## 7. Мост `IStream::Read` → `PeerLink`

Ограничение: `IStream::Read` — блокирующий синхронный вызов на COM-потоке.
Данные приходят через `PeerLink`, который принадлежит **GUI-потоку Qt** и может
быть тронут только оттуда.

Запрос идёт **от COM-потока**, а не от GUI: при одном запросе в полёте (§8)
никто не знает, что данные понадобятся, пока Проводник их не попросил.

```
        Qt GUI thread                        ║        COM STA thread
                                             ║
                                             ║   IStream::Read(cb)
                                             ║     │
   FileTransferService.request_read ◀────────╫─────┤ post_to_service(entry, offset, cb)
     (QueuedConnection)                      ║     │
       │                                     ║     ▼
       └─ send FILE_READ ──────▶             ║   ChunkPipe.read(buf, cb)
                                             ║        БЛОКИРУЕТСЯ на Condition
 PeerLink.readyRead                          ║        пока данных нет
   → FileTransferService._on_chunk           ║           │
       │                                     ║           │
       └─ ChunkPipe.push(entry, offset, buf) ─╫──────────▶┤ просыпается
            (никогда не блокирует)           ║           ▼
                                             ║   возвращает байты Проводнику
                                             ║
                                             ║   отмена / Release / EndOperation
   FileTransferService.on_pipe_closed ◀──────╫──── ChunkPipe.close(reason)
     (QueuedConnection)                      ║        notify_all() → Read просыпается
       → send TRANSFER_END{...}              ║           немедленно, не по таймауту
```

Два сообщения из COM-потока в GUI — `request_read` и `on_pipe_closed` — и оба
идут через одну и ту же функцию `post_to_service()`. Больше COM-поток наружу не
обращается никак. Если спайк 2 покажет, что окно необходимо (§8), GUI начнёт
выдавать следующий `FILE_READ` сразу после `push`, не дожидаясь запроса, — и
именно тогда понадобится правило против устаревшего чанка после `Seek`.

### Инварианты, каждый из которых обязан проверяться тестом

| Инвариант | Чем обеспечен |
|---|---|
| COM-поток не трогает `QSslSocket` и ни один `QObject` | `ChunkPipe` — чистый `threading.Lock`/`Condition`, без Qt. Правило 3 boundary-теста |
| GUI-поток никогда не блокируется на очереди | GUI только `push()`; `read()` вызывает исключительно COM-поток |
| единственный путь COM → GUI | одна функция `post_to_service()` поверх `QMetaObject.invokeMethod(..., Qt.QueuedConnection)` |
| отмена мгновенна | `close()` делает `notify_all()`; заблокированный `Read` возвращает управление, а не ждёт таймаута |
| потолок памяти доказуем | `ChunkPipe` отказывает в `push` выше окна; тест утверждает, что глубина не превышала окно |

### Почему выделенный STA-поток

STA сериализует входящие COM-вызовы через свой насос сообщений, поэтому наш
объект не обязан быть потокобезопасным для конкурентных вызовов, а GUI-поток не
блокируется **по построению**, а не как следствие тонкости маршалинга.
`OleInitialize` и `OleSetClipboard` вызываются на этом потоке; он же крутит
насос.

Названная альтернатива: free-threaded marshaler
(`CoCreateFreeThreadedMarshaler`), при котором вызовы обслуживаются на
RPC-потоках. Применяется, только если спайк 1 покажет, что STA не работает.

Спайк 1 обязан записать **id потока каждого вызова** — иначе «GUI не
блокируется» останется предположением.

### Чтение с диска на стороне PC1

Чтение выполняется в GUI-потоке PC1. Обоснование: один чанк — сотни килобайт,
что на порядки меньше «длинной операции». Порог назван, а не подразумевается:
план обязан измерить p99 времени кадра GUI под нагрузкой, и если измерение
покажет заметную задержку — тот же приём `ChunkPipe` переворачивается в
читающий поток на стороне отправителя **без изменения протокола**. Запасной
выход назван заранее, чтобы его не пришлось изобретать под давлением.

## 8. Протокол

### Шесть типов сообщений

```
FILE_OFFER(10)      PC1→PC2  {transfer_id, entries[], total_bytes, skipped[], drop_effect}
TRANSFER_BEGIN(11)  PC2→PC1  {transfer_id, session_id}
FILE_READ(12)       PC2→PC1  {transfer_id, entry_index, offset, length}
FILE_CHUNK(13)      PC1→PC2  {transfer_id, entry_index, offset} + сырые байты
FILE_ERROR(14)      PC1→PC2  {transfer_id, entry_index, offset, reason}
TRANSFER_END(15)    PC2→PC1  {transfer_id, session_id, status}
```

`status ∈ {completed, cancelled, failed}`.

`entries[]`: `{path, kind, size, mtime_ns}`, где `kind ∈ {file, directory}`.
`skipped[]`: `{path, reason}` — для reparse points и отказов доступа при обходе.

Разбор заголовков — тем же строгим стилем, что уже принят в
`clipboard/offer.py:from_dict`: проверка типов, не приведение, и `bool`
исключён из `int` (`seq=True` не должен молча сойти за `seq=1`).

### Чего в протоколе нет — и почему

| Предлагалось | Почему нет |
|---|---|
| `FILE_ACCEPT` / `FILE_REJECT` | согласие — это первый `FILE_READ`; отказ — просто не читать. Разрывать нечего |
| `FILE_BEGIN` / `FILE_END` | манифест уже размечает записи, а `offset` явный. Второе разграничение было бы вторым источником истины |
| `TRANSFER_CANCEL` | `TRANSFER_END{status:"cancelled"}` несёт это. Один путь завершения вместо двух |
| `TRANSFER_ERROR` | у ошибки всегда есть сторона: чтение падает → `FILE_ERROR`; сессия падает → `TRANSFER_END{failed}` |
| длина чанка в заголовке | длина blob задана кадром. Дубль однажды разошёлся бы |

### Решающее свойство: чтения идемпотентны и адресуются смещением

`FILE_READ{entry_index, offset, length}` против неизменяемого **манифеста** —
не последовательный поток. Отсюда бесплатно:

- `IStream::Seek` поддерживается без изменения протокола;
- Проводник может читать записи в любом порядке и держать несколько потоков;
- повторный `Ctrl+V` — не новая передача, а новые чтения того же манифеста, и
  «дублирующийся transfer_id» перестаёт быть отказом вообще;
- resume позже добавляется дешево, хотя в M1 и отложен.

### Кадрирование и потолки

`MAX_FILE_CHUNK_BYTES` вводится отдельно от `MAX_FRAME_BYTES` и заметно ниже
его. Отправитель отвергает `FILE_READ` с `length > MAX_FILE_CHUNK_BYTES`;
получатель отвергает `FILE_CHUNK`, чей blob больше запрошенного. Оба отказа —
`FILE_ERROR`, а не разрыв связи.

### Начальная схема потока: один запрос в полёте

**Correctness-путь M1 — ровно один outstanding logical read:**

```
IStream::Read(cb) → FILE_READ → ожидание → FILE_CHUNK → вернуть Проводнику
```

Окно и предвыборка **не входят в дизайн как инвариант**. `256 KiB × 8` —
гипотеза, а не решение.

Причина осторожности — `Seek`. Если бы мы заранее запросили смещения
`N+1…N+8`, а Проводник сделал `Seek`, потребовалось бы отменять и
инвалидировать устаревшие чанки — целый пласт состояния, которого при одном
запросе в полёте не существует вовсе.

Порог зафиксирован ДО измерения, чтобы неудобное число нельзя было
перетолковать в разрешение добавлять механизмы:

- **>= 70% потолка голого TCP в той же сети** - пропускная способность
  достаточна, окно не добавляется;
- **< 70%** - это НЕ разрешение добавить окно, а предписание сначала
  локализовать узкое место: RTT запрос/ответ, задержка чтения с диска, p99
  GUI, `bytesToWrite`, пропускная способность TLS с обойдённым мостом,
  промежутки heartbeat.

Окно разрешено проектировать **только** если evidence показывает, что узкое
место действительно в последовательном круге `FILE_READ → FILE_CHUNK`. Узкое
место в чтении с диска, в GUI-потоке, в сокете или в TLS исправляется там, где
оно живёт, а не маскируется окном. И тогда вместе с ним обязательно вводится
правило, не позволяющее устаревшему чанку попасть в `IStream` после `Seek`:
поколение (`generation`) либо read-token в `FILE_READ`/`FILE_CHUNK`, который
получатель сверяет перед `push`. Без такого правила окно не добавляется.

Потолок памяти при одном запросе в полёте: **размер одного чанка**. Это
сильнее, чем требовалось.

### Backpressure структурно, а не политикой

Тянет получатель. Отправитель отвечает только на запросы, а запросов в полёте
не больше окна (в M1 — один). Быстрый отправитель **не может** съесть память
медленного получателя: это не правило, которое надо соблюдать, а
невозможность. Дополнительно `PeerLink` получает `setReadBufferSize()` и
водораздел по `bytesToWrite()`, чтобы то же ограничение действовало и на уровне
сокета.

## 9. Конечные автоматы

### PC2 — сессия вставки (владелец: `FileTransferService`)

```
IDLE
 │ FILE_OFFER принят, манифест прошёл sanitize целиком
 ▼
OFFERED ───────── новый FILE_OFFER ───────▶ IDLE (объявление в буфере заменено)
 │ Проводник: StartOperation / GetData(FILECONTENTS) → первый IStream
 ▼
TRANSFERRING ◀── новый FILE_OFFER НЕ прерывает (§12, сценарий 1)
 │
 ├─ сессия завершена (источник истины — ниже) ──▶ COMPLETED
 ├─ отмена пользователем ──────────────────────▶ CANCELLED
 ├─ PeerLink.disconnected ─────────────────────▶ DISCONNECTED
 └─ FILE_ERROR ────────────────────────────────▶ FAILED
      во всех четырёх: очереди закрыты, Read'ы разбужены, TRANSFER_END отправлен
```

### Завершение сессии — источник истины определяет спайк 1

Ранняя формулировка «все `IStream` освобождены и манифест исчерпан →
`COMPLETED`» **этой спекой не фиксируется**. Она неверна по конструкции:
`Release` одного потока означает конец жизни этого потока, а не конец операции
Проводника.

Спайк 1 обязан установить фактический жизненный цикл:

```
StartOperation → GetData → IStream Read / Seek / Release → EndOperation
```

- Если `IDataObjectAsyncCapability::EndOperation` окажется надёжным сигналом
  завершения операции оболочки, **он становится единственным авторитетным
  сигналом завершения сессии.**
- `Release` отдельного `IStream` в любом случае означает только конец жизни
  этого потока, а не всей сессии передачи.
- Отмена: записать, чем именно она проявляется — статусом в `EndOperation`,
  `Release`, прекращением `Read` или комбинацией.

После спайка в §9 вносится **один** источник истины. До того автомат считается
незакрытым в этой точке — см. §22, вопрос 1.

### PC1 — снимок (владелец: `SnapshotRegistry`)

```
NONE
 │ локальный Ctrl+C на файлах → обход → манифест → FILE_OFFER
 ▼
PUBLISHED(transfer_id)     снимок = пути и метаданные. Файлы НЕ открыты
 │ первый FILE_READ для записи
 ▼
SERVING                    дескриптор записи открыт и удерживается (§10)
 │ завершение сессии / разрыв / вытеснение / источник изменился
 ▼
RELEASED                   дескрипторы закрыты
```

### Кто инициирует каждый переход

| Переход | Инициатор |
|---|---|
| `NONE → PUBLISHED` | пользователь PC1 (`Ctrl+C`) |
| `IDLE → OFFERED` | PC1, сообщением `FILE_OFFER` |
| `OFFERED → TRANSFERRING` | **Проводник PC2** — ни наш код, ни пользователь напрямую |
| `PUBLISHED → SERVING` | PC2, первым `FILE_READ` |
| `→ COMPLETED` | Проводник PC2 (сигнал уточняется спайком 1) |
| `→ CANCELLED` | пользователь PC2 через Проводник |
| `→ DISCONNECTED` | сеть |
| `→ FAILED` | PC1 (`FILE_ERROR`: файл исчез, изменился, нет прав) |

### Удержание снимков на PC1

`SnapshotRegistry` хранит снимок по `transfer_id`. Новый `Ctrl+C` создаёт новый
`transfer_id` и новый снимок, но **не вытесняет** тот, у которого есть активная
сессия. Правило: удерживается последний `PUBLISHED` плюс все `SERVING`; потолок
4; вытесняется самый старый неактивный. Снимки содержат пути и метаданные, но
не байты файлов, поэтому потолок дешёвый.

## 10. Согласованность источника

Проверка `(size, mtime_ns)` необходима, но сама по себе **не создаёт
неизменяемый байтовый снимок**. Измерение (§2, факт 7) показало это прямо: пока
мы держим дескриптор, другой процесс свободно пишет и усекает файл.

### Выбранная модель

```
первый FILE_READ данной записи
  → сверить (size, mtime_ns) с манифестом
  → открыть файл ОДИН раз
  → удерживать дескриптор на время жизни соответствующей сессии
  → все последующие offset-чтения идут через ЭТОТ дескриптор
  → закрыть по завершении сессии, отмене или ошибке
```

На каждом чтении сверяется `os.fstat(fd)` — **через наш дескриптор, не через
путь**. Расхождение по размеру или `mtime_ns` даёт
`FILE_ERROR{reason: "source_changed"}`.

### Что эта модель даёт, и чего не даёт

**Даёт, и это измерено:**

- **подмена пути невозможна.** `os.remove` и `os.rename` на удерживаемом файле
  отказывают с `winerror 32`. Классический TOCTOU «проверили путь, потом
  открыли другой файл» здесь не существует: путь открывается один раз, дальше
  работа идёт с файловым объектом.
- **проверка не обращается к пути повторно**, поэтому TOCTOU внутри самой
  проверки тоже отсутствует.

**Не даёт, и это записано как ограничение, а не замаскировано:**

- **байтовой неизменяемости нет.** Другой процесс может писать в файл и усекать
  его, пока мы читаем. Мы это обнаруживаем через `fstat` и отказываем, но
  предотвратить не можем.
- **изменение той же длины с восстановленным `mtime`** (некоторые инструменты
  так делают намеренно) не обнаруживается. Остаточный риск, названный явно —
  §21, R10.

### Отклонённая альтернатива: `FILE_SHARE_READ` без `FILE_SHARE_WRITE`

Настоящий байтовый снимок достижим: открыть через `CreateFileW` с
`dwShareMode = FILE_SHARE_READ` (Python `open()` этого не умеет, нужен `ctypes`
плюс `msvcrt.open_osfhandle`). Тогда чужая запись отказывает.

**Отклонено.** Объявление живёт до следующего `Ctrl+C`, то есть часами. За это
время пользователь, скопировавший свой документ, не смог бы сохранить его в
своём же редакторе, и причина была бы совершенно неочевидной. Запирать файлы
пользователя ради согласованности передачи, которая может не начаться никогда,
— плохая сделка. Волюмный теневой снимок (VSS) требует администратора и
отпадает по той же причине, что WebDAV.

### Терминология

В коде, журнале и интерфейсе эта модель называется **удерживаемым дескриптором
с обнаружением изменений**, а не «immutable snapshot». Неизменяемым является
**манифест**, а не байты. Разница существенна: называть одно другим значило бы
обещать пользователю гарантию, которой нет.

## 11. Безопасность путей

Проводник пишет файлы, но `cFileName` в `FILEGROUPDESCRIPTORW` строим мы.
**Это единственное место, где безопасность целиком наша**, поэтому оно описано
подробно.

`sanitize_relative_path()` отвергает:

- абсолютные пути: буква диска (`C:\`, `C:`), ведущий `\` или `/`, UNC (`\\`)
- любой сегмент `..` или `.`
- пустой сегмент после нормализации `/` → `\`
- зарезервированные имена устройств Windows посегментно: `CON`, `PRN`, `AUX`,
  `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9` — с расширением и без, без учёта регистра
- завершающую точку или пробел в сегменте: Windows их отбрасывает, а значит две
  разные записи могут схлопнуться в одну
- символы `< > : " | ? *` и диапазон `0x00`–`0x1F`
- длину свыше 259 UTF-16 единиц (граница `WCHAR[MAX_PATH]`, §6)
- чрезмерную глубину вложенности
- дубликаты после NFC-нормализации и приведения регистра: файловая система
  Windows регистронезависима, поэтому две записи, различающиеся только
  регистром, столкнулись бы
- превышение потолка числа записей и суммарного размера

Порядок важен: нормализация Unicode выполняется **до** остальных проверок, и
после неё проверки прогоняются заново — иначе нормализация могла бы создать
запрещённую последовательность уже после того, как её проверили.

**Отвергается манифест целиком, а не отдельная запись.** Неполное дерево хуже
честного отказа: пользователь, получивший 9 файлов из 10, об этом не узнает.

Каждое правило проверяется мутационно: при удалённом условии соответствующий
тест обязан упасть. Это отдельная задача в плане, а не подразумеваемое
свойство.

### Reparse points на источнике

Обход дерева **не следует** за junction и symlink: иначе папка с junction на
`C:\Windows` выгрузила бы операционную систему. Такие записи попадают в
`skipped[]` с причиной, и PC2 сообщает, сколько ссылок пропущено. Воссоздавать
ссылки на приёмнике не пытаемся — на Windows это требует прав.

## 12. Сценарии

**Сценарий 1. Буфер сменился во время передачи.** PC1 копирует `fileB`, пока
идёт передача `fileA`. Передача `fileA` **не затрагивается**, и это держится
структурно, а не правилом: `IDataObject`, уже отданный Проводнику, несёт свой
`transfer_id` внутри себя и неизменяем; новое объявление публикует новый
объект; `SnapshotRegistry` на PC1 не вытесняет снимок с активной сессией (§9).

**Сценарий 2. Пир отключился во время передачи.** `PeerLink.disconnected` →
сервис закрывает все очереди → заблокированные `Read` просыпаются и возвращают
код ошибки → Проводник показывает свой диалог ошибки копирования и убирает свой
частичный файл сам. Наша очистка не нужна, потому что частичным файлом владеет
Проводник. В журнал — событие, в трей — разрыв. Переподключение работает по
существующим правилам `coordinator.py`; передача не возобновляется (resume
отложен), но повторный `Ctrl+V` после восстановления связи просто работает,
потому что чтения адресуются смещением и не зависят от прежней сессии.

**Сценарий 3. Повторный `Ctrl+V`.** Проводник снова вызывает `GetData`,
получает новые `IStream`, идут новые чтения того же манифеста. Новая сессия,
тот же снимок. Отдельного отказа «дублирующийся transfer_id» не существует.

**Сценарий 4. Файл на приёмнике уже существует.** Решает Проводник своим родным
диалогом «заменить / пропустить / оба». Нашей политики перезаписи в M1 нет
вовсе, и это прямое следствие выбора архитектуры C.

**Сценарий 5. Источник исчез или изменился между копированием и вставкой.**
`FILE_ERROR{source_changed}` либо `{source_missing}` → `FAILED` → Проводник
показывает ошибку. Обнаружение — по §10.

## 13. Совместимость протокола

`HELLO` получает `capabilities`, например `["clipboard/1", "files/1"]`.
`PROTOCOL_MINOR` поднимается 0 → 1. **Major остаётся 1.**

- отсутствие ключа `capabilities` = старый пир = `["clipboard/1"]`;
- `FILE_*` не отправляется никогда, если пир не заявил `files/1`;
- поэтому старый пир не получает неизвестный тип, не попадает в `WireError` →
  `_fail()`, и его буфер обмена продолжает работать.

### Почему `FILE_OFFER` — отдельный тип, а не новый дескриптор внутри `OFFER`

Старый пир, получив `OFFER` незнакомой формы, прогонит его через
`ClipboardOffer.from_dict`, та бросит `ValueError`, а `handle_message` её
**не ловит** — необработанное исключение внутри Qt-слота. Это не теория, а
текущее поведение `clipboard/service.py`. Отдельный тип сообщения — не вопрос
вкуса.

### Почему одно TLS-соединение, а не второе

Второе соединение дало бы изоляцию (объёмный трафик не задерживал бы `PING`),
но удвоило бы поверхность доверия, брандмауэра и переподключения и потребовало
бы повторной аутентификации. При pull-схеме очередь записи ограничена одним
чанком, поэтому head-of-line blocking — **измеримая** величина, а не надежда:
против `HEARTBEAT_MS = 10_000` и `SILENCE_LIMIT_MS = 30_000` запас
несопоставимый. Плюс бесплатный бонус: `coordinator._on_message` перезаводит
сторожа молчания на **любом** сообщении, включая файловые.

Один канал, две логические подсистемы.

## 14. Петля буфера обмена — готовый дефект, который надо закрыть

`windows_backend.is_private()` (`clipboard/windows_backend.py:47`) ищет в
`formats()` ровно строку `application/x-duo-input-origin`. Но Qt показывает
незнакомый нативный формат как `application/x-qt-windows-mime;value="<имя>"` —
точного совпадения не будет, маркер не сработает, и **наша собственная
публикация вернётся к нам как локальное копирование**.

Закрывается двумя половинами:

1. наш `IDataObject` объявляет формат маркера происхождения;
2. `is_private()` учится узнавать и обёрнутое написание.

Мутационный тест: убрать любую половину — тест обязан упасть. Это ровно тот
класс дефекта, который в этом проекте встречается чаще всего (работающий код, до
которого production не дотягивается), поэтому он назван здесь, а не оставлен на
усмотрение реализации.

## 15. Приватность и диагностика

- **Байты файлов не логируются никогда**, ни в каком режиме.
- **Полные пути не логируются.** В журнал и в список событий идут basename и
  размер. Полный путь раскрывает структуру диска пользователя, а для
  диагностики достаточно имени.
- staging не существует: файлы читаются из своего исходного места. Свойство
  «содержимое не пишется на диск» сохраняется дословно.
- В нашем процессе никогда не живёт больше одного чанка на сессию.
- Диагностика без постоянного подробного журнала: `bytes_sent`,
  `bytes_received`, `current_rate`, `elapsed`, `chunk_count`,
  `pipe_high_water`. Всё это числа, не содержимое.

## 16. Модель потоков

| Поток | Что ему принадлежит |
|---|---|
| Qt GUI | `PeerLink`, `QSslSocket`, `FileTransferService`, `SnapshotRegistry`, чтение файлов-источников, все сигналы `QObject`, интерфейс |
| COM STA (один, создаётся по необходимости) | `OleInitialize`, `OleSetClipboard`, `IDataObject`, `IEnumFORMATETC`, все экземпляры `IStream`, насос сообщений |
| общее, свободное от Qt | `ChunkPipe` (`threading.Lock`/`Condition`), замороженный манифест |

Потоков ровно два. Это первая многопоточность в `configurator/` вообще — §2
спеки буфера зафиксировал, что ни `QThread`, ни `asyncio`, ни `threading` в
приложении не встречались. Поэтому граница между потоками описана инвариантами
(§7) и защищена boundary-тестом (§5), а не соглашением.

## 17. Интерфейс

Минимум для M1, на существующей странице «Общий буфер»:

- строка состояния передачи: `Получение 1.4 ГБ / 8.2 ГБ`
- кнопка «Отмена»
- переключатель «Передача файлов» в трее становится настоящим
  (`ui/tray.py:63` сегодня `setEnabled(False)`)
- ключ `QSettings` `clipboard/files_enabled` перестаёт быть всегда-false

Сложный менеджер передач сейчас не проектируется. Транспорт и сервис выдают
достаточные события — `transfer_started`, `transfer_progress`,
`transfer_completed`, `transfer_failed`, `transfer_cancelled` — а интерфейс
является их потребителем. Обратной зависимости нет.

Строки идут в оба каталога переводов, русский по умолчанию, как задано в
`i18n.py`. Идентификаторы протокола не переводятся.

## 18. macOS

В M1 не реализуется. Windows-специфичный код изолирован в `windows_files.py` и
`windows_com.py`, и это проверяется boundary-тестом, а не обещается.

Ядро (`model.py`, `paths.py`, `pipe.py`, `scanner.py`, `service.py`,
`source.py`) работает с `TransferManifest`, `TransferEntry` и `ChunkPipe`, а не
с `CF_HDROP` и `FILEDESCRIPTORW`.

**Честная оговорка о будущем.** Аналог на macOS — `NSFilePromiseProvider`. Он
документирован прежде всего для drag-and-drop; поддерживает ли Finder обещание
файла на `⌘V`, неизвестно, и установить это можно только спайком на машине с
macOS. Эта спека **не** утверждает, что M1-абстракция закроет macOS без
открытий. Она утверждает меньшее и проверяемое: **транспорт, протокол и
валидация путей от Windows не зависят**, поэтому переписывать при появлении
macOS придётся адаптер, а не ядро.

`paths.py` при этом останется Windows-строгим и на macOS: запреты Windows
являются надмножеством, и ослаблять их под другую платформу незачем.

## 19. Тестирование

Архитектура выбрана в том числе за то, что большая часть логики в ней — чистые
функции и чистые объекты без Qt, сети и COM.

### Модульные, без Qt и без сети

- **`paths.py`** — каждое правило §11 отдельным тестом: `../evil.exe`,
  `..\evil.exe`, `C:\...`, `\\server\share`, `/foo`, `CON`, `nul.txt`,
  `name.`, `name `, управляющие символы, 300 UTF-16 единиц, дубликат по
  регистру, дубликат после NFC. **Мутационная проверка каждого правила:**
  удаляем условие — тест обязан упасть.
- **`pipe.py`** — два настоящих потока в тесте: `push`/`read`, блокировка на
  пустой очереди, пробуждение при `push`, немедленное пробуждение при
  `close()`, отказ в `push` выше окна, `read` после `close`, утверждение о том,
  что глубина никогда не превышала окно.
- **`model.py`** — round-trip манифеста, строгая валидация типов в стиле
  `offer.py` (в том числе отказ от `bool` вместо `int`), отказ на неполном
  заголовке.
- **`wire.py`** — кадрирование `FILE_CHUNK`, потолок `MAX_FILE_CHUNK_BYTES`,
  усечённый кадр, неизвестный тип.
- **capability negotiation** — `HELLO` без ключа даёт только `clipboard/1`;
  `FILE_*` не отправляется пиру без `files/1`.
- **конечный автомат** `service.py` на поддельной связи, по образцу
  `device/emulator.py`: все переходы §9, включая «новое объявление не прерывает
  идущую передачу».

### Интеграционные, на временных каталогах и настоящем TLS на loopback

`sender/` и `receiver/` во `tmp_path`, данные генерируются детерминированно —
огромные фикстуры в репозитории не хранятся.

Размеры: 0 Б, 1 Б, 1 КиБ, 1 МиБ, 100+ МиБ.
Случаи: один файл; несколько файлов; вложенные каталоги; имя в Unicode;
нулевой файл; разрыв посередине; отмена посередине; усечённый кадр;
повторный `transfer_id`; изменившийся источник; junction в дереве источника
(создаётся через `mklink /J`, тест пропускается, если недоступно).

### Тест памяти

Синтетический файл на несколько ГиБ (генерируется, на диске не хранится).
Утверждение: рост памяти процесса ограничен и не масштабируется с объёмом
переданного. `tracemalloc` для Python-части плюс грубая проверка RSS. Отдельный
маркер: тест медленный.

### Граничные тесты

Четыре правила §5. Плюс проверка, что список модулей не пуст — существующий
`test_boundaries.py` уже содержит этот приём (`_package_modules` отказывается
сообщать об успехе при нулевом обходе), и он обязателен: пустой обход однажды
уже делал эти границы зелёными, не проверяя ничего.

### Production call path — обязательная категория, а не формальность

Доминирующий дефект этого проекта — работающий код с проходящим тестом, до
которого production не дотягивается. Поэтому отдельными тестами проверяется:

- при включённом переключателе файловая подсистема действительно создаётся в
  `app.configure_runtime`, а не только существует как модуль;
- переключатель «Передача файлов» в трее поднимает и останавливает подсистему
  **через настоящий пункт меню**, а не через запись ключа настроек в обход
  интерфейса;
- пока переключатель выключен, ни один COM-объект не регистрируется в буфере
  обмена;
- `tests/packaging/test_dist.py` проверяет, что **собранный** `dist/DuoInput`
  действительно создаёт `IDataObject` — иначе `ctypes`-обратные вызовы,
  сломанные Nuitka, проявились бы только у пользователя.

### Ограничение окружения

Тесты COM и буфера обмена **не идут** под `QT_QPA_PLATFORM=offscreen`, который
установлен в `tests/ui/conftest.py`. Они получают отдельный маркер и запускаются
в настоящей сессии Windows — тот же приём, который §16.4 спеки буфера уже
применил к `QClipboard`.

Отдельно: в тестах интерфейса нельзя использовать `keyClicks` с кириллицей —
это падает с `0xC0000409` без вывода. Имена файлов в Unicode проверяются
файловыми API, а не вводом с клавиатуры.

### Ручные проверки на двух машинах, которые автотест не заменяет

`Ctrl+C` → переключение → `Ctrl+V` для: одного файла; нескольких файлов; папки
с вложенностью; файла больше 1 ГБ; отмены посередине; разрыва связи посередине.
Результат оформляется записью в `docs/superpowers/records/` по конвенции
репозитория.

Две неизвестности не смешиваются. Спайк 2 начинается только после того, как

### Спайк 1 — семантика COM и Проводника. Синтетические данные, без сети

`configurator/tests/transfer/spike_virtual_files.py`, throwaway, по конвенции
репозитория рядом с двумя существующими спайками буфера.

Отдаёт три записи, включая вложенную папку и **синтетический файл 4 ГиБ**

единственный честный прибор для «интерфейс не зависает» — движущаяся картинка
перед глазами.

Критерии, записанные **до** запуска:

| # | Что должно быть установлено |
|---|---|
| 1 | Проводник принимает объект и предлагает вставку |
| 2 | видит `FILEDESCRIPTORW`, создаёт дерево папок |
| 3 | запрашивает `FILECONTENTS` с `TYMED_ISTREAM`, а не требует `HGLOBAL` |
| 4 | `IStream::Read` вызывается **после** `Ctrl+V` и ноль раз до него |
| 5 | чтение обслуживается потоково; `Read` вправе вернуть меньше запрошенного |
| 6 | анимация Qt-окна не замирает |
| 7 | родной диалог прогресса Проводника движется и показывает правдоподобные числа |
| 8 | «Отмена» действительно прерывает чтение, и мы об этом узнаём |
| 9 | память процесса не растёт с объёмом переданного |

Помимо критериев спайк **обязан записать** — это входные данные для решений,
оставленных открытыми в §22:

- фактический `cb` каждого `Read`;
- **id потока каждого вызова** (иначе §7 остаётся предположением);
- вызывается ли `Seek`, вызывается ли `Stat`, и с какими аргументами;
- порядок запросов форматов в `GetData`;
- полный жизненный цикл операции:
  `StartOperation → GetData → Read/Seek/Release → EndOperation`;
- является ли `EndOperation` надёжным сигналом завершения операции оболочки;
- чем проявляется отмена: статусом в `EndOperation`, `Release`, прекращением
  `Read` или комбинацией.

И отдельно: **два прогона, с `IDataObjectAsyncCapability` и без него**, с
записью наблюдаемой разницы по id потоков, `StartOperation`/`EndOperation`,
порядку `GetData`, отзывчивости интерфейса, родному прогрессу и семантике
отмены. Без этих двух прогонов утверждение «интерфейс обязателен» осталось бы
теорией.

## 22. Открытые вопросы — и чем каждый закрывается

Спека сознательно оставляет три решения незакрытыми: закрыть их чтением кода
нельзя, а закрыть догадкой значило бы построить вокруг догадки подсистему.

| # | Вопрос | Закрывается |
|---|---|---|
| 1 | Что является авторитетным сигналом завершения сессии: `EndOperation`, `Release` последнего потока или комбинация? И чем проявляется отмена? | спайк 1. После него в §9 вносится **один** источник истины |
| 2 | Нужно ли окно предвыборки, и если да — какое правило защищает от устаревшего чанка после `Seek`? | спайк 2, измерением пропускной способности при одном запросе в полёте. Без измеренной необходимости окно не добавляется |
| 3 | Обязателен ли `IDataObjectAsyncCapability` для приемлемого UX? | спайк 1, двумя прогонами с записью разницы |

Всё остальное решено и зафиксировано выше: архитектура C; голый `ctypes`;
`ClipboardService` не расширяется; COM изолирован от Qt-сокета; capability
negotiation через `files/1`; major остаётся 1, minor → 1; старому пиру `FILE_*`
не отправляется; одно TLS-соединение; offset-based `FILE_READ`; `Ctrl+X`
всегда превращается в Copy; junction и symlink пропускаются; удерживаемый
дескриптор с обнаружением изменений вместо обещания неизменяемости байтов;
resume, одновременные передачи, remote Move и macOS отложены; B остаётся
запасным путём только при доказанном блокере в C.
