# Дизайн: «Расширение экрана» — переход мыши и клавиатуры через край экрана

**Дата:** 2026-10-04
**Статус:** дизайн согласован по разделам, ожидает ревью спеки
**Внутреннее имя:** `screen_extension`

## Цель

Два компьютера должны ощущаться как один расширенный рабочий стол. Курсор,
упёршийся в край экрана ПК1 со стороны соседа, при продолжении движения
переходит на ПК2 и появляется у противоположного края в соответствующей точке.
Клавиатура следует за ним. Хоткей не нужен, но остаётся.

Главное требование — **мышь нельзя потерять**. Любой отказ должен
заканчиваться не хуже, чем сегодняшнее переключение хоткеем.

## Решения, принятые при обсуждении

| Вопрос | Решение |
| --- | --- |
| Клавиатура при переходе | Следует за мышью через существующую настройку «Переключать клавиатуру и мышь вместе» (`synchronised_control`). Переход по краю — обычный переезд мыши в `move_route`. Новых флагов сцепки нет |
| Зажатая кнопка мыши у края | Край непроницаем, пока зажата любая кнопка мыши. Проверяет прошивка |
| Где живёт раскладка | У агентов (QSettings), синхронизация через платы абсолютным состоянием с версией |
| Архитектура | Вариант D: агент сообщает касание края, прошивка меряет давление и переключает |
| Отображение координат | Пропорциональное по длине обращённого края. Геометрическое с порталами — фаза 2 |
| Предварительное позиционирование курсора | Фаза 2. В MVP — передача с воротами |
| Название в UI | Флаг «Расширение экрана» |

## Как переключение работает сейчас

- Маршрутизатор один — ядро 1 U1. `Routes` (`firmware/u1_main/mapping/routes.cpp`)
  хранит `keyboard ∈ {PC1, PC2, BOTH}` и `mouse ∈ {PC1, PC2}`.
- Маршрут меняется только в `BindingEngine::move_route`
  (`firmware/u1_main/mapping/engine.cpp`): проверка допустимости → отпустить
  зажатое на покидаемом ПК → пометить физически зажатое «осиротевшим» → сменить
  маршрут → при `synchronised_` поставить ведомое устройство туда же. Хоткей —
  привязка `TOGGLE_*_ROUTE`; шаги макросов идут через `set_*_route` в тот же
  `move_route`.
- CDC-команды смены маршрута у хоста нет. Маршрут в `GET_STATUS` не сообщается.
- SPI U1↔U2: 1 МГц, кадр 64 байта (заголовок 10, CRC 2, полезная нагрузка
  до 52), U1 ведущий, кадр за проход цикла, абсолютные состояния. U2 готовит
  ответ заранее в `SpiSlave::prime()`, поэтому путь U2→U1 занимает ~1–2 мс.
- Движение мыши копится в `state_manager`, пока его не заберут:
  `poll_snapshot` держит дельты, пока не отправит.
- Обе платы имеют CDC: U1 — `ConfigService`, U2 — `AddressService` (обмен
  адресами). U1 уже шлёт хосту сообщения без запроса (`CAPTURE_EVENT`,
  `DeviceService` разбирает его в `device/service.py`).

**Новая фича не создаёт второго механизма маршрутизации.** Край — ещё один
источник запроса к `move_route`, наравне с хоткеем, макросом и профилем.

## Рассмотренные архитектуры

| | A. Агент решает | B. Прошивка считает позицию | **D. Гибрид (выбран)** | E. Программный KVM |
| --- | --- | --- | --- | --- |
| Суть | Агент меряет давление по Raw Input / event tap и шлёт `SWITCH` | U1 интегрирует дельты | Агент сообщает касание, U1 меряет давление по сырым дельтам и сам вызывает `move_route` | Агент перехватывает ввод и шлёт его по сети |
| Задержка в момент перехода | 2–20 мс (Python + CDC, +SPI) | <1 мс | ~1 мс решение + 3–10 мс передачи курсора, движение не теряется | 5–50 мс, сеть |
| Реальная позиция | да | **нет** | да | да |
| Мультимонитор, DPI | да | нет | да; по проводу идёт только `t` | да |
| Разрешения macOS для детекта | вероятно, Input Monitoring | нет | **нет** | Accessibility + Input Monitoring |
| Сеть | не нужна | не нужна | **не нужна** | на критическом пути |
| Агент завис | решение «залипает» | — | TTL касания, тайм-аут передачи | мышь потеряна |

B отвергнут: ускорение ОС нелинейно, курсор упирается в край и перестаёт
двигаться, а интеграл продолжает расти; другие источники позиции (тачпад,
`SetCursorPos` приложений) прошивке не видны. E отвергнут: он отказывается от
аппаратного HID (экран блокировки, BIOS, работа без драйверов), ставит сеть на
критический путь и требует разрешений macOS. A проигрывает D по разрешениям
macOS и по тому, кто принимает решение при зависании.

D выбран, потому что решение о переходе принимает тот, кто уже владеет
маршрутом и видит сырой ввод, а геометрию сообщает тот, кто её действительно
знает. Любой отказ деградирует ровно до поведения с хоткеем.

## 1. Последовательности и порядок операций

### Кто что знает

- **Ядро 1 U1:** сырые дельты, маршрут, зажатые кнопки. Новый чистый класс
  `EdgeArbiter` (давление, условия, кулдаун) вызывает `move_route`.
- **Ядро 0 U1:** CDC, SPI, состояние вывода (`OutputRuntime`,
  `HidStateManager`). Здесь живут ворота передачи и тайм-аут.
- **Агент:** позиция курсора, мониторы, обращённые края. Переводит `t` в свои
  координаты и ставит курсор.

### Ключевой приём упорядочивания

Ворота закрываются **командой в той же SPSC-очереди**, по которой идёт вывод.
В момент перехода ядро 1 кладёт `BeginHandoff{target, id, side, t}` в очередь
**раньше** первой команды по новому маршруту. Ядро 0 обязательно увидит ворота
до первой дельты для новой цели. Отдельный межъядерный флаг дал бы гонку.

### ПК1 → ПК2 (мышь на ПК1, сосед справа)

```
Агент ПК1        U1 ядро0          U1 ядро1             U2            Агент ПК2
 │ курсор на правом крае, вне угловых зон
 │─CDC EDGE_CONTACT{gen,→,t,threshold}─▶ ящик ─▶ контакт[PC1]
 │  (обновление ≤100 мс, TTL 250 мс)
 │                                  дельты dx>0 копятся (мышь ещё на ПК1,
 │                                  курсор упёрт — ПК1 ничего не замечает)
 │                                  порог ✓ и все условия ✓
 │                                  move_route(mouse→PC2) [+ клавиатура по синхрону]
 │                                  ├ release/orphan на ПК1 (как у хоткея)
 │                                  └ очередь: BeginHandoff{PC2,id,side,t}
 │                 ворота[PC2] закрыты; состояние мыши ПК2 копится
 │                 ─SPI LINK_EDGE_STATE{handoff id,side,t}─▶ │
 │                                                    │─CDC push HANDOFF─▶│
 │                                                    │   t → свои координаты,
 │                                                    │   SetCursorPos / CGWarp…
 │                                                    │◀─CDC HANDOFF_READY{id}─│
 │                 ◀─SPI ENDPOINT_EDGE_STATE{last_ready_id}──│
 │                 ворота[PC2] открыты → накопленное одним отчётом,
 │                 дальше обычный поток MOUSE_DELTA
```

### ПК2 → ПК1

Зеркально. Касание идёт по маршруту агент ПК2 → CDC U2 →
`ENDPOINT_EDGE_STATE` → ядро 0 U1 → ящик → ядро 1. Решение то же. Затем
`BeginHandoff{PC1}`, и U1 сам шлёт `HANDOFF` в свой CDC агенту ПК1. SPI на
критическом пути нет.

### Свойства

- Старый компьютер не получает лишнего: дельта, перешедшая порог, уже идёт по
  новому маршруту. До неё курсор ПК1 был упёрт в край.
- Новый компьютер не получает ничего до warp. Ворота держат **всё состояние
  мыши** цели — движение, кнопки и колесо. Клавиатура воротами не задерживается.
- Дельты не теряются: после `READY` приходит их сумма, то есть дистанция,
  которую рука реально прошла за ~5–10 мс.
- Ворота открываются сами через **80 мс** без `READY`. После **3 тайм-аутов
  подряд** для одной цели U1 считает агент цели отсутствующим и открывает
  ворота сразу, пока от этой цели не придёт любой `READY`.

### Бюджет задержки ПК1→ПК2 (оценка, уточняется замером)

| Шаг | Время |
| --- | --- |
| Решение на ядре 1 | <0,1 мс |
| Очередь → ядро 0 | <0,5 мс |
| SPI-кадр `LINK_EDGE_STATE` | 0,5–1 мс |
| U2 → ПК2 по CDC | ~1 мс |
| Qt, Python, warp | 1–5 мс, хвост до 20 мс |
| `HANDOFF_READY` по CDC и в ответе SPI | ~2 мс |
| Первый отчёт мыши на ПК2 | ~1 мс |
| **Итого** | **≈ 6–12 мс** |

Обратный путь короче на ~2 мс.

### Арбитраж с хоткеем

Все смены маршрута сериализуются на ядре 1 через `move_route`. Каждая смена
получает новый `id` передачи. Переход по краю кладёт в очередь `BeginHandoff`,
любая другая смена (хоткей, макрос, профиль) — `CancelHandoff`, который
открывает ворота. `READY` со старым `id` игнорируется. Поздний `HANDOFF` на
машине, откуда мышь уже уехала, безвреден: курсор неактивной машины просто
встаёт у края.

## 2. Модель раскладки и перевод координат

### Пропорциональное отображение

Обращённый край источника целиком отображается на противоположный край цели
целиком. Мёртвых зон нет. Следствие: **цели не нужна чужая геометрия**. По
проводу идут только `(сторона, t)`, каждая машина переводит `t` по своему
текущему списку мониторов. Рассинхрон раскладок, смена DPI или отключение
монитора у соседа не уводят курсор в пустоту.

### Модель

```
Layout   { version u32, origin_id u64, machines[] }
Machine  { machine_id    — стабильный; тот же origin_id, что у буфера обмена
           os
           offset (x,y)  — положение блока в единицах раскладки
           displays[]    — снимок от самой машины, только для рисования }
Display  { native_rect, scale } → logical_rect = native_rect / scale
```

- Пользователь двигает **машины целиком**. Внутреннее расположение мониторов
  каждая машина берёт из своей ОС.
- Единица раскладки — логический пиксель: на Windows физический пиксель /
  (DPI/96), на macOS точка.
- Соседство выводится из положения блоков: `сторона → сосед`. В MVP на
  стороне не больше одного соседа.

### Обращённый край и параметр t

Обращённый край машины на стороне S — объединение внешних отрезков мониторов на
этой стороне. Отрезок внешний, если шаг на 1 пиксель наружу не попадает ни в
один монитор той же машины. Разрывы между отрезками выбрасываются.

`t` — доля длины дуги вдоль этих отрезков в логических единицах, u16 0…65535.

- **Источник:** нативная позиция → отрезок → логическая длина от начала
  края → `t`.
- **Цель:** `t` → дуга на обращённом крае противоположной стороны → отрезок и
  логическая позиция → нативные координаты, с отступом 2 логических пикселя
  внутрь.
- **Угловые зоны:** касание не сообщается в пределах 10 логических пикселей от
  концов каждого отрезка обращённого края. Броски курсора в углы («Пуск»,
  горячие углы macOS, «закрыть» развёрнутого окна) не должны переводить курсор.

Пример: ПК1 2560×1440@100%, ПК2 1920×1080 справа. Y=720 → `t`=0,5 → на ПК2
левый край, Y=540, X=2. При масштабе ПК2 150% логический Y=360, нативный 540.

## 3. Обнаружение намерения

### Давление, а не время у края или скорость

Время у края отвергнуто: у края законно стоят (полосы прокрутки, «закрыть»).
Скорость отвергнута: бросок к кнопке в углу тоже быстрый. Давление наружу при
упёртом курсоре в обычной работе не возникает.

### Алгоритм `EdgeArbiter` (ядро 1, на каждый отчёт мыши)

```
o = составляющая (dx,dy) наружу по стороне касания   (справа: dx; слева: −dx; снизу: dy; сверху: −dy)
если o > 0:  acc += o;  last_out = now
если o < 0:  acc = 0
если now − last_out > 200 мс: acc = 0
если acc ≥ threshold и условия ✓: переход
```

Движение вдоль края `acc` не сбрасывает. Новое касание (новый `gen`) обнуляет
`acc`.

**Ступени порога** (стартовые значения, уточняются замером):

| Ступень | Отсчётов | ≈ при 1000 DPI |
| --- | --- | --- |
| Нет | 1 | первый толчок |
| Низкое | 40 | 1 мм |
| **Среднее (по умолчанию)** | 120 | 3 мм |
| Высокое | 300 | 7,5 мм |

### Условия перехода (все в прошивке, по порядку)

1. Есть касание, то есть агент включил режим. Нет агента — нет режима.
2. Касание пришло от машины, которой сейчас принадлежит мышь.
3. Касание свежее: TTL 250 мс.
4. `gen` касания новее последней передачи курсора.
5. Не зажата ни одна кнопка мыши.
6. Цель жива. Для ПК2: U2 отвечает по SPI, его USB смонтирован, и от U2
   приходит `ENDPOINT_EDGE_STATE` (признак новой прошивки). Для ПК1: USB U1
   сконфигурирован и не в suspend.
7. С последней смены маршрута любого происхождения прошло ≥ 250 мс.

### Автомат прошивки

```
           касание валидно                acc ≥ порог, условия ✓
   IDLE ───────────────────▶ PRESSING ───────────────────────────▶ HANDOFF
    ▲  ◀── касание пропало / ──┘                                     │ READY(id) или 80 мс
    │      устарело / внутрь                                         ▼
    └────────────────────── 250 мс ──────────────────────────── COOLDOWN
   любая другая смена маршрута из любого состояния → CancelHandoff → COOLDOWN
```

### Автомат агента

```
INACTIVE  (мышь не здесь — по ROUTE_STATE): касаний не шлёт; HANDOFF → warp → READY
   ▼ мышь пришла
FREE ──курсор на обращённом крае с соседом, вне угловых зон, режим не подавлен──▶ CONTACT
 ▲                                                    │ EDGE_CONTACT{gen++, side, t, threshold}
 └──── курсор ушёл → EDGE_CONTACT{active=0} ◀──────────┘ повтор раз в 100 мс; при изменении t — не чаще 60 Гц
```

- Позиция опрашивается раз в 8 мс таймером `QTimer`.
- Отдельного «разоружения» края входа нет: от ложного возврата защищают отступ
  2 пикселя, кулдаун 250 мс, условие нового `gen` и полный порог.

### Подавление касаний агентом

- **Windows:**
  - `GetClipCursor` уже виртуального экрана;
  - курсор скрыт (`GetCursorInfo` без `CURSOR_SHOWING`);
  - `GetCursorPos` вернул ошибку (защищённый рабочий стол);
  - при включённой опции — `SHQueryUserNotificationState` ∈
    {`QUNS_RUNNING_D3D_FULL_SCREEN`, `QUNS_BUSY`}.
- **macOS:**
  - при включённой опции — окно активного приложения во весь экран
    (`CGWindowListCopyWindowInfo`);
  - детект скрытого курсора — по результату спайка.

## 4. Протокол

Новая возможность `capabilities.SCREEN_EXTENSION = 16384` объявляется и U1, и
U2 в `DEVICE_INFO`. `PROTOCOL_VERSION_MINOR` не меняется. Агент шлёт новые
сообщения только плате, подтвердившей возможность.

### CDC: агент ↔ своя плата (одинаково для U1 и U2)

| Тип | Направление | Полезная нагрузка | Ответ |
| --- | --- | --- | --- |
| `EDGE_CONTACT` = 25 | хост → плата | `gen u16, active u8, side u8, neighbor u8, t u16, threshold u16` (9 байт) | нет, уведомление |
| `HANDOFF_READY` = 26 | хост → плата | `id u16` | нет, уведомление |
| `EXCHANGE_LAYOUT` = 27 | хост ↔ плата | запрос: свой `LayoutBlob` + `DesktopBlob`; ответ: `[error]` + блобы соседа | да, тихая операция |
| `HANDOFF` = 28 | плата → хост | `id u16, side u8, t u16` | — |
| `ROUTE_STATE` = 29 | плата → хост | `mouse u8, keyboard u8, reason u8` | — ; при изменении и раз в 1 с |

- `side`: 1 = слева, 2 = справа, 3 = сверху, 4 = снизу. В `EDGE_CONTACT` это
  сторона источника, в `HANDOFF` — сторона входа на цели.
- `neighbor` — номер цели (в MVP всегда «другой ПК»), задел на 3+ машины.
- `reason`: хоткей, край, макрос, профиль, хост.
- Порог едет в каждом касании, поэтому прошивке не нужно хранить настройки.
- `EDGE_CONTACT` и `HANDOFF_READY` — первые уведомления без ответа в протоколе.
  Плата не отвечает на них, а агент шлёт их **вне очереди транзакций**
  `DeviceService`, чтобы они не ждали за записью конфига.

### SPI: U1 ↔ U2

| Тип | Направление | Содержимое (абсолютное состояние) |
| --- | --- | --- |
| `LINK_EDGE_STATE` = 10 | U1 → U2 | `mouse u8, keyboard u8, reason u8, handoff_active u8, handoff_id u16, side u8, t u16` |
| `ENDPOINT_EDGE_STATE` = 11 | U2 → U1 | касание ПК2 (`gen, active, side, neighbor, t, threshold`) + `last_ready_id u16` |
| `LAYOUT_STATE` = 12 | U1 → U2 | блобы ПК1 |
| `ENDPOINT_LAYOUT_STATE` = 13 | U2 → U1 | блобы ПК2 |

Типы в двух направлениях разные: `link::is_endpoint_reply` расширяется на 11 и
13, чтобы эхо от короткого замыкания линий не принималось за ответ U2. `READY`
по SPI — не событие, а повторяемое поле `last_ready_id`.

**Приоритеты U1 в `poll_snapshot`:**
1. `LINK_EDGE_STATE`, если изменилось (открылась или закрылась передача,
   сменился маршрут).
2. Существующие ветки: адреса, клавиатура, мышь.
3. `LINK_EDGE_STATE` повтором раз в 20 мс вместо `HEARTBEAT`; `LAYOUT_STATE`
   раз в 250 мс отдельной веткой, как `HOST_ADDRESSES`.

**Приоритеты U2 в `prime()`:**
1. `ENDPOINT_EDGE_STATE` при изменении касания или `last_ready_id` и повтор
   раз в 10 мс, пока касание активно.
2. Адреса и блоб раскладки (раз в 64 ответа).
3. `ENDPOINT_STATUS`.

### Блобы (вместе 51 байт, помещаются в один SPI-кадр)

```
LayoutBlob (17 байт), общий для пары:
  version u32, origin_id u64      — побеждает старшая пара (version, origin_id)
  flags u8                        — bit0 screen_extension, bit1 fullscreen_guard
  threshold_level u8              — 0..3
  peer_side u8                    — где сосед относительно машины origin_id
  peer_offset i16                 — сдвиг блока вдоль стороны (рисование; фаза 2)
DesktopBlob (34 байта), свой у каждой машины:
  os u8, display_count u8 (≤4), по дисплею x,y,w,h i16 в логических единицах
```

Правка раскладки: `version = max(видимая) + 1`. При более чем 4 мониторах в UI
рисуются первые 4; на переход это не влияет.

### Межъядерные пути на U1

- **Ядро 0 → ядро 1:** ящик касаний на каждую цель (ПК1 из CDC, ПК2 из SPI) —
  снимок под seqlock, по образцу `core_bridge`.
- **Ядро 1 → ядро 0:** `BeginHandoff` / `CancelHandoff` в SPSC-очереди вывода.
- **Ядро 0:** ворота, тайм-аут, `last_ready_id` из обоих источников, рассылка
  `HANDOFF`, `ROUTE_STATE`, `LINK_EDGE_STATE`.

### Совместимость

- Новая U1 со старой U2: нет `ENDPOINT_EDGE_STATE` → переход по краю на ПК2 не
  выполняется, хоткей работает.
- Старая плата видит новые SPI-типы как ошибки CRC, как при обмене адресами.
  Прошивать обе платы вместе.
- Агент без `SCREEN_EXTENSION` от своей платы показывает причину и не включает
  режим.

## 5. Реализация агента

### Пакет `configurator/src/duo_input/screen/`

| Модуль | Назначение |
| --- | --- |
| `geometry.py` | Чистая модель: `Display`, обращённый край, `t ↔ точка`, «на крае?», угловые зоны, отступ |
| `probe.py` | Интерфейс `DesktopProbe`: `displays()`, `cursor()`, `warp(p)`, `suppressed()` |

| `probe_macos.py` | pyobjc: AppKit, Quartz |
| `edge_agent.py` | Автомат INACTIVE/FREE/CONTACT, опрос, `gen`, троттлинг, `HANDOFF` → warp → `READY` |
| `edge_link.py` | Связь с платой: бэкенд U1 (быстрая полоса `DeviceService`) и бэкенд U2 (`EndpointService` с постоянным портом и разбором push) |
| `layout_exchange.py` | Синхронизация блобов, по образцу `AddressExchange` |

Смена мониторов ловится сигналами Qt `screenAdded`, `screenRemoved` и
`geometryChanged`, после чего геометрия перечитывается нативным API, а
`DesktopBlob` отправляется заново.

### Windows

- `GetCursorPos`, `SetCursorPos`, `EnumDisplayMonitors` + `GetMonitorInfoW`,
  `GetDpiForMonitor(MDT_EFFECTIVE_DPI)`.
- Процесс обязан быть Per-Monitor-V2 DPI aware. При старте агент читает
  `GetThreadDpiAwarenessContext`, пишет в журнал и не включает режим, если там
  не PMv2. Проверяется в собранном Nuitka-exe.
- `probe_windows.py` вносится в разрешения `test_boundaries` на ctypes, по пути
  и с причиной.
- Скрывающаяся панель задач на обращённом крае: первый толчок показывает панель.
  Описывается в справке.

### macOS

- Позиция: `NSEvent.mouseLocation` (координаты Cocoa → CG: `y = H_main − y`).
  Без разрешений.
- Мониторы: `NSScreen.screens()` — `frame` и `backingScaleFactor`.
- Курсор: `CGWarpMouseCursorPosition`, затем
  `CGAssociateMouseAndMouseCursorPosition(true)`. Интервал подавления
  локальных событий обнуляется через
  `CGEventSourceSetLocalEventsSuppressionInterval`, иначе после warp движение
  глохнет на ~250 мс.
- Accessibility и Input Monitoring не нужны: перехвата и инъекции событий нет.
- Полноэкранность: `CGWindowListCopyWindowInfo` (владелец и границы окна
  доступны без Screen Recording).

### Спайки (первые задачи плана; код выбрасывается)

**macOS**, на подписанной сборке:
1. `CGWarpMouseCursorPosition` из подписанного .app без разрешений TCC.
2. Подавление после warp снято: движение от U2 непрерывно сразу после warp.
3. Точки `NSScreen` и `mouseLocation` совпадают на краях при Retina + внешний
   1080p, в том числе при мониторе выше или ниже.
4. Детект скрытого курсора (`CGCursorIsVisible` или аналог) в игре или в
   относительном режиме.
5. Опрос `mouseLocation` на 125 Гц из Python нагружает CPU ≤ 1%.
6. Поведение warp и `mouseLocation` на экране блокировки.

Если не подтвердится пункт 1 или 2, запасной путь для Mac-стороны — абсолютный
HID-отчёт от прошивки. Это решение принимается по результатам спайка, отдельно.

**Windows:** PMv2 в собранном exe; `GetCursorPos`/`SetCursorPos` на
защищённом рабочем столе.

## 6. Отказы и восстановление

**Инвариант:** маршрут живёт в прошивке, ворота открываются сами по тайм-ауту
ядра 0, не завися ни от агента, ни от USB, ни от SPI, ни от сети. Исходов у
отказа два:

- **(а)** переход по краю не случился — работает хоткей;
- **(б)** переход случился без установки курсора — мышь на новой машине,
  курсор там, где стоял.

| Ситуация | Исход |
| --- | --- |
| Агент соседа не запущен | (б) через 80 мс; после 3 тайм-аутов подряд — сразу |
| Свой агент не запущен или умер | (а); TTL касания 250 мс |
| Агент цели завис | (б); поздний `READY` со старым id игнорируется |
| `READY` потерян | SPI повторит через ≤10 мс; в худшем случае (б) |
| Сеть отключена | ничего не меняется |
| Провод U1↔U2 оборван | (а) в сторону ПК2; дальше существующая обработка потери связи |
| ПК цели спит, USB в suspend | (а); хоткей и пробуждение как раньше |
| Быстро туда-обратно | кулдаун 250 мс + новый `gen` + полный порог; дребезга нет |
| Хоткей во время передачи | `CancelHandoff` в той же очереди; побеждает последнее действие |
| Хоткей и край в одном проходе | ровно одно переключение (кулдаун) |
| Раскладка изменилась на одной стороне | синхронизация ≤ 5 с; `t` всегда по своим мониторам |
| Монитор отключён или подключён, док-станция | перечитать мониторы; курсор вне всех мониторов → на ближайший |
| Экран блокировки Windows | уйти по краю нельзя (а), войти можно (б) |
| Экран блокировки macOS | то же; уточняется спайком |
| Игра, захват курсора, относительный режим | подавление → (а) |
| RDP или VM в окне | как обычное приложение; захват мыши → (а) |
| RDP на весь экран | по опции полноэкранных приложений |
| U1 перезагрузился | маршрут по умолчанию; агенты заново шлют блобы и касания |
| Приложение перезапустилось посреди передачи | (б) |
| Обе стороны одновременно правят раскладку | побеждает старшая (version, origin_id), проигравший UI перерисовывается |
| Зажата кнопка мыши | край непроницаем |

### Наблюдаемость

- **Счётчики прошивки в `GET_DIAGNOSTICS`:**
  - число переходов по краю;
  - тайм-ауты ворот;
  - максимальная и средняя задержка `BeginHandoff → READY`;
  - отброшенные касания неактивной машины;
  - отказы из-за мёртвой цели, зажатой кнопки и кулдауна.
- **Журнал агента:** строка на каждое касание (`gen`), каждый `HANDOFF id`
  (получен, warp выполнен, `READY` отправлен) и каждое подавление с причиной.
  Успех печатается так же, как отказ.

## 7. UI

### MVP: страница «Расширение экрана»

Отдельная страница в навигации рядом с «Общий буфер». Настройки действуют
сразу, как у общего буфера, и не требуют записи в устройство. Поэтому их нет
на странице «Мышь», где всё применяется кнопкой «Write to device».

```
┌ Расширение экрана ────────────────────────────────────────────────┐
│ [✓] Расширение экрана                                             │
│     Курсор переходит на второй компьютер через край экрана,       │
│     как на второй монитор. Хоткей продолжает работать.            │
│   ┌───────────────┐┌──────────┐                                   │
│   │ ┌────┐┌─────┐ ││ Второй   │  ← перетаскивается, прилипает     │
│   │ │ 1  ││  2  │ ││ 1920×1080│    к одной из 4 сторон            │

│   [✓] Не переходить из полноэкранных приложений и игр             │
│   ● Работает. Клавиатура переключается вместе с мышью.            │
└───────────────────────────────────────────────────────────────────┘
```

- **Блоки** рисуются по `DesktopBlob` в логических размерах. Свой блок
  неподвижен, блок соседа перетаскивается. Сдвиг вдоль стороны в MVP только
  визуальный; подпись: «край отображается на край целиком».
- **Выпадающий список** стороны дублирует перетаскивание (доступность с
  клавиатуры).
- **Строка состояния** всегда называет причину:
  - «Работает»;
  - «На втором компьютере не запущен Duo Input»;
  - «Прошивка плат не поддерживает — обновите обе платы»;
  - «Плата не подключена»;
  - «Windows: процесс не в режиме Per-Monitor DPI»;
  - «Сосед ещё не прислал раскладку».
- **Строка про клавиатуру** при выключенном синхроне — ссылка на страницу
  «Мышь»: «Клавиатура остаётся на месте — включите „Переключать клавиатуру и
  мышь вместе“».
- **Сосед недоступен:** его блок рисуется пунктиром по последнему описанию.
- **Настройки** (флаг, сторона, порог, полноэкранная опция) общие для пары и
  лежат в `LayoutBlob`. Полноэкранную защиту каждая машина применяет к своим
  окнам.
- **Страница одинакова на ПК1 и ПК2.** Строки — через `self.tr` и
  `tools/update_translations.py`.

### Мутации

Удаляется каждое из 7 условий, тайм-аут ворот, порядок «ворота раньше
движения», угловые зоны, сброс при движении внутрь, игнор старого id. На каждую
мутацию краснеет хотя бы один тест.

### Приёмка на железе (с журналами обеих сторон)

1. ПК1→ПК2 и обратно на всех четырёх сторонах; Y=50% → 50%; без рывков.
2. Задержка `BeginHandoff → READY` по счётчику: медиана ≤ 12 мс, 99-й
   перцентиль ≤ 30 мс; 0 тайм-аутов за 200 переходов.
3. 2 минуты работы у края при среднем сопротивлении — 0 случайных переходов.
4. Бросок в угол — перехода нет.
5. Перетаскивание окна к краю — перехода нет.
6. Хоткей во время толчка — ровно одно переключение.
7. Агент цели закрыт → мышь на цели через ≤ 80 мс.
8. Провод U1↔U2 выдернут → перехода нет, хоткей работает.
9. Цель спит → перехода нет.
10. Отключение и подключение монитора; док-станция.
11. Экран блокировки на каждой стороне.
12. Полноэкранная игра, относительный режим.
13. RDP в окне и на весь экран.
14. Зажатый Shift → переход по краю → Shift на старом ПК отпущен.
